## 1. 背景与目标

### 1.1 业务背景

随着公司业务从单一 B2C 商城扩展到 B2B 大客户、品牌特卖、自营+第三方混合等多种业务形态，订单中心作为交易核心服务，需要承担以下职责：

1. **统一订单模型**：掩盖不同业态（实物、虚拟、预售）的差异，对外提供一致的订单视图与生命周期。
2. **高并发交易**：双 11 / 618 等大促峰值预计 **QPS 8000+**（P99 < 200ms），全年 0 宕机目标。
3. **财务一致性**：支付、退款、对账必须强一致，不允许出现「钱包已扣、订单未支付」或反之的情况。

### 1.2 范围

本说明书覆盖订单中心 **v1.2** 版本，**IN** 范围如下：

- 用户注册 / 登录 / Token 刷新 / 个人信息维护（手机号 + 密码方案）
- 商品中心：商品列表、详情、上下架
- 订单中心：下单、支付、取消、查询

**OUT** 范围（其他模块负责）：

- 库存管理（由 `inventory-service` 负责）
- 支付通道（由 `payment-gateway` 负责）
- 物流（由 `logistics-service` 负责）
- 推荐 / 搜索（由 `recommend-service` 负责）

### 1.3 名词术语

| 术语 | 定义 |
|---|---|
| SPU | Standard Product Unit，商品标准化单元 |
| SKU | Stock Keeping Unit，库存进出计量的基本单元 |
| 订单号 | 形如 `ORD-yyyyMMdd-XXXXXXXX` 16 位字符串 |
| 幂等键 | 调用方生成的 UUID，相同 key 在幂等窗口内仅生效一次 |
| Token | JWT，HS256 签名，Header.Payload.Signature |

## 2. 用户角色与场景

### 2.1 角色清单

| 角色 | 描述 | 主要场景 |
|---|---|---|
| 未登录访客 | 匿名访问者 | 浏览商品、注册 |
| 注册用户 | 已完成手机号+密码注册 | 下单、支付、改密 |
| VIP 用户 | 月消费 ≥ 5000 元 | 优先发货、专属客服 |
| 风控审计员 | 内部运营 | 异常订单审核（v1.3 起） |
| 系统管理员 | 内部运维 | 配置限流阈值、查看监控 |

### 2.2 关键场景描述

**场景 1：新用户注册 → 首单**
1. 用户通过 `/api/v1/users/register` 完成手机号注册（需先过短信码）。
2. 系统分配 user_id，写入数据库，返回 `201 Created`。
3. 用户浏览商品列表，挑选 SKU 加入购物车。
4. 提交订单 `/api/v1/orders`，调用库存服务预占库存，成功返回订单号。
5. 用户在 30 分钟内完成支付，超时订单自动取消。

**场景 2：重复支付防护（幂等性）**
1. 用户在弱网环境点击「支付」按钮，可能因为超时而多次重试。
2. 前端必须生成幂等键 `idempotency_key`（UUID v4），传入 Header。
3. 后端 5 分钟内对相同 key 只处理一次，避免重复扣款。
4. 第二次相同 key 的请求，返回首次的响应结果，不抛错。

## 3. 功能性需求

### 3.1 用户管理（FR-USER）

| 编号 | 优先级 | 描述 |
|---|---|---|
| FR-USER-01 | P0 | 手机号 + 密码注册：手机号格式校验（11 位 1[3-9]开头）、密码强度（≥8 位含大小写数字特殊符号）|
| FR-USER-02 | P0 | 账号密码登录：5 次错误锁定 30 分钟，登录成功返回 JWT 双 Token |
| FR-USER-03 | P0 | Refresh Token 刷新 Access Token；Refresh 过期需重新登录 |
| FR-USER-04 | P1 | 查询当前用户信息（`GET /users/me`）|
| FR-USER-05 | P1 | 修改密码：旧密码 + 新密码（强度校验），成功后 15 分钟内旧 token 全部失效 |

**异常处理**：
- 手机号格式错误 → 400 INVALID_PHONE_FORMAT
- 密码强度不足 → 400 WEAK_PASSWORD
- 手机号已注册 → 409 PHONE_ALREADY_REGISTERED
- 连续 5 次登录失败 → 423 LOCKED

### 3.2 商品中心（FR-PRODUCT）

| 编号 | 优先级 | 描述 |
|---|---|---|
| FR-PRODUCT-01 | P0 | 商品列表：支持关键词、分类、价格区间、排序、分页；仅展示已上架 |
| FR-PRODUCT-02 | P0 | 商品详情：返回 SPU + SKU 列表 + 库存 + 评价数；下架商品 404 |
| FR-PRODUCT-03 | P2 | 商品搜索（基于 ES，v1.3 接入，本期不实现）|

**性能**：
- 列表查询 P99 < 100ms（命中缓存）
- 详情查询 P99 < 50ms

### 3.3 订单中心（FR-ORDER）

| 编号 | 优先级 | 描述 |
|---|---|---|
| FR-ORDER-01 | P0 | 创建订单：根据 SKU + 数量 + 地址，调用库存预占，返回订单号 |
| FR-ORDER-02 | P0 | 订单支付：必须传幂等键，相同 key 5 分钟内幂等；成功后状态置 PAID |
| FR-ORDER-03 | P0 | 订单取消：PENDING 或 PAID 可取消，PAID 取消触发原路退款（1-3 工作日）|
| FR-ORDER-04 | P1 | 订单查询：按状态、时间筛选，仅当前用户可查自己订单 |
| FR-ORDER-05 | P1 | 订单详情：根据 ID 查详情，校验订单所有者 |
| FR-ORDER-06 | P2 | 订单超时自动取消：30 分钟未支付自动置 CANCELLED，释放库存 |

**限流**：
- 单用户下单：1 分钟内 ≤ 10 单
- 全平台下单：1 秒内 ≤ 1000 单（令牌桶）

**订单状态机**：

```
        PENDING ──支付成功──> PAID ──发货──> SHIPPED ──签收──> COMPLETED
           │                  │                                    │
           │                  └──取消（已支付）──> CANCELLED ───退款──> REFUNDED
           └──取消（待支付）──> CANCELLED
```

## 4. 非功能性需求

### 4.1 性能

| 接口 | P99 延迟 | QPS 上限 |
|---|---|---|
| `/users/login` | < 200ms | 500 |
| `/users/refresh` | < 50ms | 2000 |
| `/products` | < 100ms（缓存命中） | 3000 |
| `/orders` POST | < 300ms | 800 |
| `/orders/{id}` GET | < 80ms | 1500 |

### 4.2 安全

1. **传输安全**：全站 HTTPS，内部 RPC 使用 mTLS。
2. **数据加密**：用户密码 bcrypt（cost=12），手机号存储 AES-256-GCM。
3. **注入防护**：所有 DB 查询使用参数化；前端展示 HTML 转义。
4. **限流**：基于用户 ID + IP 双维度令牌桶，单用户超过阈值 1 分钟熔断。
5. **审计日志**：登录、改密、下单、支付、取消 5 类敏感操作全量记录，保留 ≥ 180 天。

### 4.3 可用性

- 整体目标 99.95%（年宕机 ≤ 4.38 小时）
- 订单服务 DB 双 AZ 主从切换 ≤ 30 秒
- 缓存失效后降级到 DB，不得出现「缓存击穿打到 DB」

## 5. 验收标准

### 5.1 用户模块验收

- [ ] 注册：合法手机号 + 强密码 → 201 + UUID；非法手机号 → 400；已注册手机号 → 409
- [ ] 登录：5 次错误锁定账号 30 分钟，错误信息不能泄露「用户不存在」或「密码错误」细节
- [ ] Refresh：refresh_token 过期 → 401；refresh_token 有效 → 新 access_token
- [ ] me：未带 token → 401；带有效 token → 200 + 用户信息
- [ ] 改密：弱密码 → 400；旧密码错 → 403；成功后旧 token 立即失效

### 5.2 订单模块验收

- [ ] 下单：库存不足 → 400；触发限流 → 429；正常下单 → 201 + 订单号
- [ ] 支付：相同 idempotency_key 5 分钟内第二次 → 返回首次结果，不重复扣款
- [ ] 取消：PENDING → CANCELLED 立即返回；PAID → CANCELLED + 退款流程启动
- [ ] 订单所有权：A 用户查 B 用户订单 → 403
- [ ] 超时取消：PENDING 30 分钟未支付 → 系统自动置 CANCELLED

## 6. 风险与依赖

| 风险 | 影响 | 应对策略 |
|---|---|---|
| 短信通道故障 | 注册链路中断 | 邮件备用通道 + 人工客服兜底 |
| 第三方支付通道不稳定 | 支付失败 | 多通道热备，自动切换 |
| 数据库大表（订单 ≥ 10 亿） | 性能下降 | 按月分表，查询自动路由 |
| 大促瞬时流量 | 系统雪崩 | 提前压测 + 弹性扩容预案 |

**外部依赖**：

- 短信网关（云通信公司）
- 支付通道（微信 / 支付宝 / 银联）
- 物流 API（顺丰 / 中通 / 京东）
