# 知识库 RAG 需求与验收标准（能力12）

> 关联方案：`docs/知识库RAG接入方案.md`
> 定位：横切增强，为「缺陷分析」「用例生成」「文档解析」三处提供历史经验召回；默认关闭、零配置可体验、不可用不阻塞主流程。
> 权限模型沿用现有 RBAC：角色含 `super_admin / admin / test_manager / tester / developer / auditor / viewer`。
> 技术约束：本轮 `knowledge_chunks.embedding` 使用 **JSONB 存 float 数组**，检索在 **Python 侧计算余弦相似度**，**不引入 pgvector 扩展**。原因：`docker-compose.yml` 中 postgres 为 `postgres:16-alpine`（musl libc），不含 vector 扩展；若换成 `pgvector/pgvector:pg16`（glibc）将导致用户已有数据卷跨 libc 切换，存在损坏线上库风险。本轮坚持零基础设施变更，pgvector 仅作为未来性能优化的可选升级路径。

---

## 1. 用户故事

### 1.1 测试工程师（tester / developer）
- US-1：作为测试工程师，我希望在做缺陷分析时自动召回相似历史缺陷的根因与修复方案，以便更快定位问题，而不必每次从零分析。
- US-2：作为测试工程师，我希望生成用例时参考团队历史有效用例，以便产出的用例更贴合真实业务场景、减少"通用但无效"的用例。
- US-3：作为测试工程师，我希望在知识库管理页做一次检索效果测试，以便在上线前确认召回质量，而不需要翻看底层日志。

### 1.2 测试经理（test_manager）
- US-4：作为测试经理，我希望维护一张业务术语表（如"下单"→"create_order 接口"），以便需求/接口解析时术语被正确映射，提升结构化准确率。
- US-5：作为测试经理，我希望看到知识库的状态与各类（缺陷/用例/文档/术语）切片数量统计，以便判断知识库是否健康、是否需要重建。

### 1.3 管理员（super_admin / admin）
- US-6：作为管理员，我希望总开关（`KB_RAG_ENABLED`）默认关闭，开启后才注入知识，以便保证存量功能与升级安全不受任何影响。
- US-7：作为管理员，我希望在知识源或术语表变更后"一键重建"知识库，并看到任务进度与结果，以便低成本地让新经验生效。
- US-8：作为管理员，我希望在未配置嵌入模型时平台依然可用（自动降级为关键词检索），以便"零配置"即可体验，无需先采购模型。

## 2. 功能清单与优先级

### P0（本轮必须交付）
- F1 知识库总开关 `KB_RAG_ENABLED`（默认 false），关闭时 3 处注入点完全不拼入、主流程行为与现状一致。
- F2 知识存储：四类切片存储（`knowledge_chunks` 表，`embedding` 用 **JSONB 存 float 数组，不依赖 pgvector 扩展**）+ 四类来源切片（defect / case / doc / term），含 `kb_type`、`source_ref`、`content`、`embedding`、`meta`；检索在 Python 侧计算余弦相似度。
- F3 重建知识库：全量切片/嵌入任务（Celery 异步），状态机（就绪/重建中/完成/失败）与进度可见。
- F4 检索降级：未配置嵌入模型时自动使用关键词（BM25）检索，行为与向量检索功能对齐。
- F5 三处注入生效：缺陷分析、用例生成、文档/需求解析在开关开启时检索并拼入 top-k 上下文，且结果可观测。
- F6 知识库管理页：状态、四分类统计、一键重建、检索效果测试。
- F7 业务术语表 CRUD（增删改查）+ API，重建时纳入 term 类切片。

### P1（建议本轮，可协商）
- F8 检索结果命中高亮 / 相似度阈值可调。
- F9 增量重建（仅变更来源差异重建），减少全量成本。
- F10 术语表批量导入（CSV）。

### P2（不在本轮强制范围）
- F11 多知识库空间/租户隔离。
- F12 检索结果人工反馈与排序优化（RLHF 式）。
- F13 知识来源自动定时同步（复用现有定时任务能力，但本轮不默认挂）。

## 3. 验收标准（AC）— 可点击验证

> 约定：验收前确保环境已启动、`knowledge_chunks` 与 `knowledge_terms` 表已创建（**JSONB 向量列，无需 pgvector 扩展**）。凡涉及"主流程"，指关闭开关时的现有缺陷分析/用例生成/文档解析行为。

### A. 开关关闭时的行为（F1）
- **AC-A1**：在配置中将 `KB_RAG_ENABLED=false`（默认值）并重启服务后，进入任意一次"缺陷分析"，其输出结果与"升级前无知识库"时**逐字一致**（不含任何"历史相似缺陷"段落），且无新增的检索日志报错。
- **AC-A2**：`KB_RAG_ENABLED=false` 下，打开"用例生成"与"文档/需求解析"，三者输出均**不出现**知识召回内容，响应时间相对开关开启不增加（波动在 ±10% 内）。
- **AC-A3**：管理页"知识库总开关"显示为**关闭**；即便底层已有 `knowledge_chunks` 数据，注入点仍不拼入（开关优先于数据存在性）。

### B. 无嵌入模型时的降级行为（F4）
- **AC-B1**：将嵌入模型配置项置空（或未配置 `embedding` use_case），点击"一键重建"，任务成功完成，状态最终为"完成"，且四分类切片数量 > 0（`doc` 类至少含术语表条目数）。
- **AC-B2**：在降级（无嵌入）状态下执行"检索效果测试"输入"登录失败"，返回 top-k 片段，每条含 `kb_type`/`source_ref`/相似度（或关键词得分），且能召回包含"登录"关键词的 chunk。
- **AC-B3**：降级状态下，缺陷分析开启注入后仍能召回历史缺陷（按关键词），输出中出现"历史相似缺陷"段落并附来源引用；主流程不报错、不超时（见 NFR）。

### C. 重建（F3）
- **AC-C1**：在知识库管理页点击【重建知识库】，任务提交后状态立即变为"重建中"；完成后分类统计**分别显示** 缺陷 / 用例 / 文档 / 术语 四类切片数量（四数之和 = `knowledge_chunks` 总行数）。
- **AC-C2**：重建过程中再次点击【重建知识库】，系统**拒绝重复提交**并提示"已有重建任务进行中"（状态仍为"重建中"），不产生第二个任务。
- **AC-C3**：重建失败（如 embedding 计算异常 / DB 写入失败）时状态变为"失败"并展示错误摘要；此时开关保持原值，三处注入仍按"上次成功"或"关闭"状态执行，不导致主流程 500。

### D. 检索效果测试（F6）
- **AC-D1**：在管理页"检索测试"框输入一段缺陷日志摘要并提交，3 秒内返回 top-k（默认 k=5）结果，每条显示来源分类图标、来源引用（如 `defect#1024`）、匹配内容摘要、得分。
- **AC-D2**：切换"仅看缺陷/仅看用例/仅看文档/仅看术语"筛选后，返回结果**仅含**所选 `kb_type`，且数量不超过总 top-k。

### E. 术语表 CRUD（F7）
- **AC-E1**：在术语表页点击【新增】，填写"业务词=下单、技术含义=create_order 接口、适用范围=接口解析"，保存后列表**立即出现**该条目，且刷新页面后仍在（落库成功）。
- **AC-E2**：对一条已有术语点击【编辑】修改"技术含义"并保存，列表与后续检索命中的术语内容同步更新；重建后该 term chunk 的 `content` 反映新值。
- **AC-E3**：选中一条术语点击【删除】并确认，列表**移除**该条目；重建后 `knowledge_chunks` 中对应 `kb_type=term` 且 `source_ref` 指向该条目的 chunk 被清除。
- **AC-E4**：新增重复的"业务词"（与已有相同）时，系统**拒绝保存**并提示重复，不产生两条同名术语。

### F. 三处注入生效的可观测表现（F5）
- **AC-F1（缺陷分析）**：`KB_RAG_ENABLED=true` 且知识库已重建，对一条已知历史缺陷现象做分析，输出中**出现**"历史相似缺陷"区块，列出 ≥1 条历史缺陷并标注来源 `defect#id`；关闭开关后该区块消失（对照 AC-A1）。
- **AC-F2（用例生成）**：开关开启下对某接口生成用例，输出中**出现**"参考历史用例"引用（含 `case#id` 或用例名）；生成的用例数量或场景明显引用了历史有效用例模板，而非纯通用模板。
- **AC-F3（文档/需求解析）**：开关开启且术语表含"下单→create_order"后，解析一份出现"下单"的需求文档，输出结构化结果中"下单"被映射/标注为 `create_order`（可在解析结果或调试信息中观测到术语替换命中）。
- **AC-F4（可观测性）**：以上三处任意一次注入发生时，后端日志打印一条含 `kb_inject=true`、`kb_type`、召回条数、耗时 ms 的结构化日志，便于 QA 与运维核对注入确实发生。

### G. 权限（见 NFR-权限）
- **AC-G1**：以 `tester` 身份登录，知识库管理页的【重建知识库】按钮**不可点击/接口返回 403**；术语表【新增/编辑/删除】同样被拒（403）。
- **AC-G2**：以 `test_manager` 身份登录，可进行术语表 CRUD 与查看统计，但【重建知识库】仍被拒（403），提示需管理员操作。
- **AC-G3**：以 `super_admin` / `admin` 身份登录，重建、统计查看、术语表 CRUD 全部可用；重建接口返回 2xx。

### H. 升级零风险与注入失败不阻塞
- **AC-H1（升级零风险）**：在不修改 `docker-compose.yml`、不重建 postgres 容器、不删除数据卷的前提下，仅重建 backend 镜像/进程即可完成升级；服务启动后 `init_db` 自动建出 `knowledge_chunks` 与 `knowledge_terms` 两张新表；升级前后既有的业务数据（用户、测试运行记录、历史缺陷等）**全部保留且可正常访问**。
- **AC-H2（注入失败不阻塞）**：当知识库为空、检索调用抛异常、或嵌入模型调用超时（> 2s）时，缺陷分析与用例生成**仍能正常产出最终结果**（仅日志记录降级并打 `kb_inject=false`，不向前端返回错误、不中断主流程、不出现 500）。

## 4. 非功能要求（NFR）

- **性能**：单次检索（top-k，k≤10）P95 响应时间 **< 1s**（向量/关键词均适用）；注入环节额外耗时 **< 500ms**，不显著拉长缺陷分析/用例生成主链路（主链路整体波动 ≤ 15%）。
- **失败降级**：①知识库不可用（表缺失 / 检索异常 / 嵌入模型调用超时 > 2s）时，注入点**静默跳过**并打 `kb_inject=false` 日志，主流程正常返回（不 500、不阻塞，见 AC-H2）；②无嵌入模型自动降级关键词检索（见 AC-B）；③重建失败不影响线上注入（见 AC-C3）。
- **权限**：重建知识库、查看统计需 `super_admin / admin`；术语表 CRUD 需 `super_admin / admin / test_manager`；只读查看（状态、统计、检索测试）对 `tester / developer` 开放；`viewer / auditor` 仅可查看，不可操作。
- **数据一致性**：重建为全量覆盖式（先清后写），避免脏数据累积；术语表变更后须重建才生效（在管理页给出"术语已变更，建议重建"提示）。
- **可观测**：提供知识库状态、最近一次重建时间/耗时/状态、累计切片数、最近一次注入命中率（近 N 次调用的注入命中比例）指标，便于运维。
- **零配置**：未配置任何嵌入模型时，平台核心功能与知识库"检索测试/降级注入"均可用，仅召回精度下降，不抛错。
- **兼容性**：复用现有 Postgres 16（`postgres:16-alpine`），`embedding` 以 JSONB 存储、余弦相似度在 Python 侧计算，**不依赖 pgvector 扩展、不引入新的独立存储组件**；复用现有 `ModelRouter` 与 `use_case` 路由，不改模型调用框架。
- **部署约束**：本轮升级**不得要求更换 postgres 镜像**（保持 `postgres:16-alpine`，不换 `pgvector/pgvector:pg16`）或**迁移/重建数据卷**；仅重建 backend 即可完成，确保已有业务数据零风险（见 AC-H1）。

## 5. 明确不做的范围（本轮）

- 不引入独立向量数据库（如 Milvus/Qdrant），也不启用 pgvector 扩展；本轮仅用 **JSONB 向量列 + Python 侧余弦相似度**实现检索（pgvector 留作未来可选性能升级）。
- 不实现多租户 / 多知识库空间隔离（F11）。
- 不做检索结果的人工反馈闭环与排序自学习（F12）。
- 不默认挂载知识源自动定时同步（F13），如需同步沿用现有定时任务手动配置。
- 不在本轮替换既有缺陷分析/用例生成/文档解析的**核心算法**，RAG 仅作为上下文增强拼入，不改变现有输出结构与既有验收。
- 不提供知识库内容的在线编辑/人工上传文档（本轮知识来源仅来自既有表与术语表，F10 批量导入列为 P1 可协商）。
- 不修改 RBAC 角色体系本身，仅复用现有角色做权限收敛。
