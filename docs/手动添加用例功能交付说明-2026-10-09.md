# 手动添加用例功能交付说明

## 入口与操作流程

1. 进入「测试资产 → 用例管理与评审」，选择项目，点击顶部带 `Plus` 图标的「手动添加用例」。列表没有结果时也提供入口。项目工作区的「项目用例」页提供相同入口。
2. 在右侧抽屉录入标题、模块/目录、说明、优先级、用例类型、标签、关联需求文档、需求编号/链接、前置条件、步骤和预期结果。
3. 标题、至少一个操作步骤、预期结果必填；空格不算内容。步骤可新增、删除、上移和下移，至少保留一个，最多 100 个。
4. 「保存用例」保存并关闭；「保存并继续添加」保存后清空标题、说明、前置条件、步骤与预期，保留目录、优先级、类型、标签和需求关联，方便连续录入。
5. 保存后切换到全部用例、清除筛选并回到第一页，滚动定位新增行，显示绿色高亮和「新添加」标记 15 秒。用例以人工来源、手工执行、草稿状态保存，可继续编辑和提交评审。
6. 同项目已有同名用例时，表单底部列出已有用例的标题和目录。再次保存需要点击「仍然添加」，可点击「返回修改」取消；不会覆盖已有用例。
7. 抽屉取消、关闭、Esc、站内路由离开均拦截未保存内容；刷新和关闭标签页使用浏览器原生提示。保存过程中阻止关闭和重复提交。请求失败保留表单内容。

使用既有 Vue 3、TypeScript、Element Plus、图标和主题变量。管理员、测试经理、测试工程师可以录入；其他角色不显示创建入口，后端保持角色和项目写入权限检查。

## 新增接口

| 方法与路径 | 功能 | 返回 |
| --- | --- | --- |
| `GET /api/cases/manual/options?project_id=<UUID>` | 获取指定项目全部目录、标签和需求文档选项，不受用例列表分页限制 | `{code:0,data:{folders:string[],tags:string[],requirements:[{id,filename}]},message:"ok"}` |
| `POST /api/cases` | 创建人工录入用例，并原子保存首个内容版本 | `{code:0,data:<现有用例资产结构>,message:"用例已保存为草稿"}` |

创建请求示例：

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "title": "未登录用户无法提交订单",
  "description": "未认证场景回归",
  "folder": "订单 / 提交",
  "preconditions": "购物车有商品，用户未登录",
  "steps": ["进入购物车页面", "点击提交订单"],
  "expected_result": "跳转至登录页，订单未被创建",
  "priority": "P1",
  "case_type": "negative",
  "tags": ["冒烟", "认证"],
  "requirement_doc_id": null,
  "requirement_ref": "REQ-102",
  "allow_duplicate": false
}
```

标题上限 500 字符，目录上限 200 字符，每步上限 5000 字符，说明、前置条件、预期各上限 10000 字符，标签最多 20 个、每个最多 40 字符，需求编号/链接上限 500 字符。优先级 `P0/P1/P2/P3`，类型 `functional/positive/negative/boundary/exception`。关联需求文档必须属于同一项目。

重复提醒返回 HTTP 409：

```json
{
  "detail": {
    "code": "CASE_DUPLICATE",
    "message": "当前项目已存在同名用例，请检查后确认是否继续添加",
    "duplicates": [{"id": "已有用例UUID", "title": "未登录用户无法提交订单", "folder": "订单 / 提交"}]
  }
}
```

确认后以 `allow_duplicate:true` 重新提交。重复判断按项目和去掉首尾空格、不区分大小写的标题进行，包括已归档用例；返回最多 10 条匹配提醒。创建时锁定项目记录，避免同时人工添加时绕过提醒。无效输入返回 422，项目不存在返回 404，无角色或项目写权限返回 403。

## 新增数据结构与存储映射

- 后端请求结构：`CreateManualCaseRequest`；前端：`CreateManualCasePayload`、`ManualCaseType`、`ManualCaseOptions`。
- 沿用 `test_case_assets`，没有新增数据库表或迁移。基础字段保存至现有标题、目录、优先级、类型、标签等列。
- `request_data = {preconditions, steps:string[], requirement_ref, requirement_doc_id?}`，数组顺序即步骤顺序；`expected_result = {text:string}`。
- `source=manual`、`execution_kind=manual`、`status=draft`、`review_state=draft`、`version=1`；`generation_context={channel:"manual_entry"}`；记录当前创建人。
- `test_case_asset_versions` 追加 `change_type=created` 的首版快照，保留前置条件、步骤、预期和关联需求；现有版本与评审机制继续使用。
- 修复已有来源追溯接口的返回逻辑，使详情能够展示创建人和关联需求文档；详情支持查看、编辑前置条件。

## 验证

- `npm run build`：TypeScript 检查和生产构建通过。
- 后端 62 项相关回归通过，包含人工录入的有效与无效输入、步骤顺序、首版快照、重复确认、需求追溯、角色及项目隔离，以及已有用例库、评审和权限回归。
- 浏览器 14 项检查通过：空列表入口、必填校验、关闭保护、路由保护、刷新保护、步骤增删排序、连续保存与列表高亮、重复提醒、重复确认、详情读取、放弃输入、手机布局、项目工作区入口、项目用例详情链接；无页面运行异常。
- 真实 PostgreSQL 与实际 JWT 认证链路验收通过：创建、重复提醒、列表、选项、版本、关联需求及提交评审。事务结束时回滚全部验收数据。

后端复验：

```sh
cd backend
python -m pytest -q tests/test_manual_case_creation.py tests/test_case_library_experience.py tests/test_basic_case_flow.py tests/test_enterprise_access.py tests/test_redesign_support_contracts.py
```

前端浏览器脚本需要可用的 Playwright 和 Chromium/Chrome。启动 `frontend` 开发服务后执行 `node tests/manual-case.e2e.mjs`；通过 `FRONTEND_URL` 指定地址（默认 `http://127.0.0.1:3100`），`PLAYWRIGHT_MODULE` 指定已有 Playwright 模块路径，`BROWSER_PATH` 指定已有 Chrome/Edge 可执行文件路径。脚本模拟业务 API，截图输出到 `frontend/test-results/`。

实际数据库链路验收：`docker exec -w /app aitp-backend python tests/manual_verify_manual_case.py`。脚本使用独立事务验证创建、重复提醒、列表、选项、版本、关联需求和提交评审，最终回滚全部验收记录。
