## 一、产品目标

这 5 个能力围绕「**从用例资产到执行闭环**」的最后一公里，解决三个核心问题：

1. **降低脚本编写门槛**：测试人员不需要手写 Python / SQL / Cron 表达式，自然语言描述意图即可生成可执行脚本，大幅降低对测试开发技能的依赖。
2. **打通数据准备与清理链路**：测试前置/后置动作（参数加密、签名、数据提取、数据库准备）从手工操作变为 AI 自动化，消除测试执行中最耗时的"胶水代码"环节。
3. **实现测试全生命周期闭环**：从用例生成 → 脚本注入 → 定时调度 → 执行 → 失败分析，形成完整的 AI 驱动的自动化测试链路，让失败的测试不只是"标红"而是能给出根因。

## 二、用户故事

### 能力5：AI 生成前置脚本

| 编号 | 用户故事 | 验收标准 |
|------|---------|---------|
| US5-1 | 作为测试工程师，我希望能用自然语言描述参数预处理需求（如"对 username 做 base64 编码"），让 AI 自动生成 Python 前置脚本，这样我就不用手写编码逻辑 | 输入自然语言 → 返回可执行 Python 脚本片段，脚本中包含明确的变量读写说明 |
| US5-2 | 作为测试工程师，我希望生成的脚本能自动嵌入到用例资产的 `pre_script` 字段中，并在用例详情页预览和编辑 | 脚本生成后自动填充到用例资产详情页的 pre_script 编辑区，支持手动修改 |
| US5-3 | 作为测试经理，我希望能对 AI 生成的前置脚本进行审核和回归测试，确保脚本逻辑符合预期 | 脚本执行后可查看执行日志，判断脚本是否按预期修改了请求参数 |

### 能力6：AI 生成后置脚本

| 编号 | 用户故事 | 验收标准 |
|------|---------|---------|
| US6-1 | 作为测试工程师，我希望用自然语言描述需要从响应中提取的数据（如"提取 token 字段到 auth_token"），AI 自动生成 JSONPath/正则提取脚本 | 输入自然语言和响应示例 → 返回包含提取逻辑的 Python 脚本 |
| US6-2 | 作为测试工程师，我希望 AI 能根据预期结果自动生成断言脚本（如"检查 status 等于 success"），并支持断言失败时的详细错误信息 | 自然语言断言需求 → 生成可执行的 assert 代码，失败时输出预期 vs 实际对比 |
| US6-3 | 作为场景编排用户，我希望后置脚本提取的变量能自动注入到场景的 extract 配置中，实现步骤间数据传递 | 在场景步骤中生成后置脚本后，提取变量自动注册到步骤的 extract 字段 |

### 能力7：AI 生成 SQL 脚本

| 编号 | 用户故事 | 验收标准 |
|------|---------|---------|
| US7-1 | 作为测试工程师，我希望能描述数据准备需求（如"插入一条测试用户"），AI 自动生成 SQL 并支持预览和执行 | 输入自然语言 + 可选表结构信息 → 生成 SQL 语句，支持预览和一键执行 |
| US7-2 | 作为测试工程师，我希望能连接数据库获取真实表结构，AI 基于表结构生成更准确的 SQL | 配置数据库连接 → AI 获取表结构 → 基于真实结构生成 SQL |
| US7-3 | 作为测试经理，我希望 SQL 脚本执行前有安全校验（禁止 DROP/TRUNCATE 等危险操作），防止误操作 | 危险 SQL 语句被拦截并提示，仅允许 SELECT/INSERT/UPDATE/DELETE（可配置白名单） |

### 能力8：AI 生成定时任务

| 编号 | 用户故事 | 验收标准 |
|------|---------|---------|
| US8-1 | 作为测试经理，我希望能用自然语言描述调度规则（如"每周一至周五上午10点执行"），AI 自动转为 Cron 表达式并创建定时任务 | 输入自然语言 → 生成 Cron 表达式 → 预览下次执行时间 → 确认创建 |
| US8-2 | 作为测试工程师，我希望能将定时任务关联到已有的测试场景或测试用例，定时自动执行并查看历史结果 | 定时任务关联场景/用例 → 按计划自动触发 → 执行历史可追溯 |
| US8-3 | 作为项目管理员，我希望能暂停/启用/编辑定时任务，并查看任务的下次执行时间和执行历史 | 定时任务列表支持启用/禁用开关，显示下次执行时间、最近执行状态 |

### 能力9：AI 分析测试报告

| 编号 | 用户故事 | 验收标准 |
|------|---------|---------|
| US9-1 | 作为测试工程师，当用例执行失败时，我希望 AI 自动分析请求/响应/日志，给出问题定位和根因分析 | 失败用例 → 点击"AI 分析" → 返回根因分析 + 修复建议 + 置信度 |
| US9-2 | 作为测试经理，我希望能查看测试报告摘要（通过率、失败分布、趋势），AI 自动生成文字总结和改进建议 | 报告页面展示 AI 生成的摘要（200-500字），包含关键数据和改进方向 |
| US9-3 | 作为开发人员，我希望能对比同一用例在不同执行中的差异，识别回归问题 | 选择两次执行 → AI 对比差异 → 输出变更点 + 回归风险提示 |

- 应用到用例后自动填充 `pre_script` 或 `post_script` 字段

## 五、与现有系统衔接

### 5.1 数据模型变更

#### 5.1.1 扩展现有表

**TestCaseAsset（test_case_assets）新增字段：**

```sql
ALTER TABLE test_case_assets ADD COLUMN pre_script TEXT;
ALTER TABLE test_case_assets ADD COLUMN post_script TEXT;
ALTER TABLE test_case_assets ADD COLUMN sql_script TEXT;
```

- `pre_script`：前置 Python 脚本（能力5）
- `post_script`：后置 Python 脚本（能力6）
- `sql_script`：数据准备 SQL 脚本（能力7）

**ModelRouting（model_routing）新增字段：**

```sql
ALTER TABLE model_routing ADD COLUMN script_generation_model_id VARCHAR(64);
ALTER TABLE model_routing ADD COLUMN sql_generation_model_id VARCHAR(64);
ALTER TABLE model_routing ADD COLUMN report_analysis_model_id VARCHAR(64);
```

- 三个字段均为 `nullable=True`，兼容老数据
- 运行时降级策略：为 NULL 时使用 `case_generation_model_id` 或 `fallback_model_id`

#### 5.1.2 新增表

**scheduled_tasks（定时任务表）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | 主键 |

| name | VARCHAR(200) | 任务名称 |
| description | TEXT | 描述 |
| nl_schedule | TEXT | 原始自然语言调度描述 |
| cron_expression | VARCHAR(100) | 解析后的 Cron 表达式 |
| target_type | VARCHAR(20) | scenario / case_collection |
| target_id | UUID | 关联的场景 ID 或用例集 ID |
| target_config | JSONB | 关联配置（用例ID列表等） |

## 六、待确认问题

| 编号 | 问题 | 优先级 | 建议方案 |
|------|------|--------|---------|
| Q1 | `test_cases` 表（执行表）是否需要 `pre_script`/`post_script`？当前模型中该表无此字段，脚本是存在 `test_case_assets` 还是同步到 `test_cases`？ | 高 | 建议仅存于 `test_case_assets`，执行时从资产读取脚本注入到执行上下文。避免双写一致性问题 |
| Q2 | 脚本沙箱执行的安全边界？Python `exec()` 有安全风险，需要多严格的沙箱？ | 高 | MVP 使用 RestrictedPython 或 Docker 沙箱容器执行。至少限制文件系统/网络访问 |
| Q3 | 数据库连接信息如何存储？数据库密码的加密方式？ | 高 | 建议复用 `ai_model_configs` 的 AES-256 加密方案，连接信息存 JSONB 字段 |
| Q4 | 定时任务的 Celery Beat 动态调度方案？Django-Celery-Beat 还是自定义 scheduler？ | 中 | 建议使用 `celery-beat` + `database scheduler`，通过数据库表动态管理任务 |
| Q5 | SQL 安全白名单的粒度？是项目级还是全局级？ | 中 | 建议项目级配置，存入 `projects.quality_gate_config` 扩展 |
| Q6 | 脚本生成是否需要流式输出（SSE）？ | 低 | MVP 不需要，后续可优化为 SSE 流式返回 |
| Q7 | 能力9 的 AI 分析是否需要调用外部知识库（如历史缺陷库）？ | 中 | MVP 仅基于当前请求/响应/日志分析，后续可接入知识库做 RAG 增强 |
| Q8 | 定时任务关联的"用例集"如何定义？是标签还是动态筛选规则？ | 中 | MVP 使用静态用例 ID 列表（JSONB），后续可扩展为动态筛选规则 |

## 附录：数据流示意

```
能力5/6 脚本生成流程：
用户输入 NL → LLM（script_generation 模型）→ 生成 Python 脚本
  → 存入 test_case_assets.pre_script / post_script
  → 执行时注入到请求上下文

能力7 SQL 生成流程：
用户输入 NL → 获取数据库表结构 → LLM（sql_generation 模型）→ 生成 SQL
  → 安全校验 → 存入 test_case_assets.sql_script / 直接执行

能力8 定时任务流程：
用户输入 NL → LLM 解析 → Cron 表达式 → 创建 scheduled_tasks 记录
  → Celery Beat 按 Cron 调度 → 触发场景/用例执行 → 记录执行历史

能力9 报告分析流程：
失败触发 / 手动触发 → 收集 test_result 数据 → LLM（report_analysis 模型）
  → 根因分析 + 修复建议 → 展示 + 可选创建缺陷
```
