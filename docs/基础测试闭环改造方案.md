# 基础测试闭环改造方案

## 目标与边界

把平台的基础路径收敛为：**需求文档 → 有出处的需求条目 → 用例草稿 → 人工评审 → 已采纳的可执行 API 用例 → 发布计划 → 选环境执行 → 请求、断言与结果**。需求推导的手工用例可以评审、管理，但只有补齐 HTTP 请求和可判定断言后才能作为 API 用例加入可执行计划。AI 仅负责提出草稿，不能替代评审或声称执行成功。代码覆盖率、UI/APP 自动化、复杂场景编排暂不纳入本轮主流程。

## 同类项目对照（以仓库公开说明为依据）

| 项目 | 可借鉴的基础能力 | 架构取舍与不足（针对本项目目标） |
| --- | --- | --- |
| [TestHub](https://github.com/chenjigang4167/testhub_platform) | 需求分析、步骤化用例、多级评审、API 集合与环境变量；Django 应用按需求、用例、评审、API 测试等拆分 | 功能面很广，还含 UI、APP、性能等；直接照搬会扩大维护面。适合借鉴职责边界，不适合迁移其 Django 数据模型。 |
| [TestMona](https://github.com/pricyproject/testmona) | 需求与用例可追溯、AI 先生成草稿再评审、用例与执行分离；React + FastAPI | 更偏通用测试管理。我们应沿用现有 FastAPI/PostgreSQL/Celery，补齐状态与证据，不重建完整 TMS。 |
| [Suitest](https://github.com/suiflex/suitest) | 手工资产与自动执行分离，确定性生成和 AI 可选、需求到测试的追踪 | MCP/多执行器能力对本阶段过重；借鉴“可复现执行不依赖 AI 即时发挥”的原则。 |
| 本平台现状 | 已有需求解析、用例资产、不可变计划修订版、API 执行器和报告 | 生成结果可能是无法执行的占位用例；采纳无评审依据；计划发布缺少可执行性门槛；无断言可误判成功；入口与文案容易把草稿当成可执行用例。 |

## 本轮实现

1. **需求分析与用例生成**：保留需求文档和条目出处；生成结果统一为项目用例草稿。没有真实 HTTP 信息时标记为手工设计用例，不构造 URL 或成功断言；取消向运行中 TestRun 直接双写。AI 不可用或输出无效时明确告知，只有用户选择规则模式才生成规则草稿。相同文档重复生成避免重复资产。
2. **用例管理与评审**：建立 `draft → pending → approved / changes_requested` 的评审状态和不可变操作记录；批准后才置为 `adopted`。编辑已批准用例后回到草稿，需重新评审。评审动作校验角色和基本内容；批量采纳不再绕过评审。
3. **API 测试**：API 用例必须有受支持的 HTTP 方法、项目环境内的相对路径和至少一个有效断言；计划加入和发布时检查。执行器遇到空断言返回失败，TLS 证书默认验证；运行明细保留请求、状态、响应和断言失败原因。
4. **界面流程**：需求页只引导“生成草稿并到用例库评审”；用例库显示类型、评审状态与评审记录，按“提交评审、批准/退回、加入计划”操作；计划页解释只能发布已采纳的可执行用例。
5. **历史数据修复**：旧需求资产中没有 URL 却写入占位 200 断言的记录降为手工草稿，旧请求完整保存在 `legacy_request_data`；旧计划修订版若仍含空请求，执行前直接阻断并提示重新发布。

## 后续阶段（本轮不承诺完成）

- 需求条目独立版本、按条目增量生成和差异评审；跨需求去重。
- 多人会签、评审指派、评论讨论与通知；编辑乐观锁。
- API 变量提取、顺序依赖、数据集、密钥托管、OpenAPI 导入差异和请求重放。
- CI/CD 门禁与代码覆盖率高级联动。

## 验收标准

- 无模型时选择 AI 生成会明确失败；选择规则模式能得到有出处的草稿，重复提交不重复造资产。
- 缺 URL 或断言的需求用例不能被误当成 API 用例执行；草稿和退回用例不能进计划。
- 评审有操作者、时间、结论和意见；批准后的任何实质编辑都要求重新评审。
- 无断言的请求不能显示为通过；有效 API 用例在已发布环境上运行后有状态码和失败原因。
- 迁移可应用到现有 PostgreSQL，现有已发布计划和历史运行快照可继续读取。
