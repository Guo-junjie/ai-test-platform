# AI 自动化测试平台企业级多角色验收报告

> 验收日期：2026-09-22
> 验收版本：`7ba024cf feat(知识问答): 增加多轮会话与历史记录`
> 验收环境：`http://192.168.125.128:3000` / `http://192.168.125.128:8000`
> 被测产品：Spring PetClinic REST（8301）、RESTful E-Commerce（8302）

## 1. 结论

当前平台已经形成“项目建档 → 文档解析 → 用例生成与评审 → 测试计划 → 执行 → 结果/缺陷/报告 → 知识沉淀”的主链路，适合在可信网络内由单一测试团队开展受控试点。需求与接口文档生成、用例资产化、环境版本快照、计划执行、报告、覆盖率报告关联、知识问答历史会话等基础能力已能工作。

平台暂未达到多部门、多项目企业生产环境的上线标准。主要阻断项不是功能数量，而是企业控制面不完整：部分业务接口允许匿名访问，项目没有成员与资源级权限隔离，当前实例使用开发模式运行，模型调用缺少成本、版本、追踪和评测治理，前端移动端不可用，数据库迁移与运行时改表并存。

综合成熟度：**2.7 / 5（可受控试点，不能直接作为企业生产级质量平台）**。

| 角色 | 评分 | 判断 |
|---|---:|---|
| 高级产品经理 | 3.2 / 5 | 主链路已形成，但跨模块上下文和企业协作闭环不足 |
| 高级软件测试工程师 | 3.1 / 5 | 核心测试流程可执行，质量门禁、数据治理和可复现性仍需加强 |
| 软件开发工程师 | 2.8 / 5 | 模块覆盖较广，类型、异常处理、前端测试和接口权限一致性欠缺 |
| 高级架构师 | 2.1 / 5 | 当前部署适合开发演示，租户隔离、生产部署、可观测性尚未成型 |
| UI/UX 设计系统总监 | 3.0 / 5 | 桌面端清晰一致，移动端、无障碍和数据表达存在明显缺陷 |
| AI Agent 开发工程师 | 2.5 / 5 | 已有多模型路由、RAG 和多轮会话，但仍是 AI 功能集合，缺少 Agent 治理运行时 |

## 2. 验收方法与范围

本轮不是只做页面巡检，而是同时进行了动态 API 验收、真实浏览器巡检、权限边界验证、历史缺陷回归和代码/部署静态审查。

- 动态 API 验收：64 个检查项，校正两个旧接口假设后，62 项通过，2 项为真实 RBAC 失败。
- 历史缺陷回归：32 个操作全部通过，包含创建、生成、执行结果检查和数据清理。
- 浏览器验收：15 个桌面路由，无控制台错误、无桌面横向溢出；3 个移动端关键页面均横向溢出。
- 权限验收：超级管理员、临时 viewer、匿名用户三种身份；临时用户、会话、用例、需求、任务和脚本记录均已清理。
- 真实产品链路：PetClinic 和 E-Commerce 的接口资产、用例、计划、运行、结果、报告及覆盖率关联均做了读取或执行验证。
- 静态审查：213 个 API 路由、31 个 API 模块、14 个数据库迁移、Docker Compose、GitHub Actions、前端类型与异常处理。

## 3. 关键缺陷清单

### P0-01 匿名用户可访问多组核心业务接口

**动态证据**：不带 Token 时，下列接口返回 HTTP 200：

- `/api/dashboard/statistics`
- `/api/dashboard/recent-runs`
- `/api/test-runs`
- `/api/results?test_run_id=...`
- `/api/reports/{run_id}`
- `/api/scheduled-tasks`
- `/api/source/configs`
- `/api/databases`
- `/api/scripts/preview`

`/api/defects` 和 `/api/coverage` 会正确返回 401，说明目前权限策略在各模块间不一致。

**静态证据**：`scheduled_tasks.py` 的查询、创建、更新、删除、启停、历史接口均没有用户依赖；`scripts.py` 的生成和预览接口没有用户依赖；`report.py` 的报告查询与手动生成大多没有用户依赖；`dashboard.py` 仅依赖数据库会话。

**风险**：未登录者可以读取项目测试资产、运行结果、环境/数据源信息和报告；部分未保护接口还可以创建或修改定时任务、触发模型调用、重新生成报告，造成数据泄漏、资源消耗和任务污染。

**验收标准**：除登录、健康检查和受控分享链接外，所有 `/api/**` 默认要求身份认证；写操作再叠加动作权限；自动化契约测试验证匿名请求为 401、越权请求为 403。

### P0-02 缺少组织、项目成员和资源级授权

数据模型与业务代码中没有 `tenant_id`、`organization_id` 或项目成员关系。动态验证中，viewer 可以读取并不属于自己的现有项目详情。知识问答会话已经按创建人隔离，这是正确实现，但同样的资源所有权策略没有覆盖项目、用例、计划、运行、报告、缺陷、知识文档等核心资源。

**风险**：多个团队共同使用时，登录用户可横向读取其他项目数据；全局角色无法表达“甲项目管理员、乙项目只读”等常见企业权限。

**验收标准**：引入组织、项目成员、项目角色与动作权限；所有资源查询必须通过统一授权服务过滤；增加跨组织、跨项目、同项目不同角色的权限矩阵测试。

### P0-03 当前运行方式是开发环境，不满足生产基线

健康检查返回 `env=development`。Compose 中后端使用 `uvicorn --reload`，前后端源代码直接挂载进容器；PostgreSQL、Redis、RabbitMQ 管理端、MinIO API/控制台和后端端口均直接映射到宿主机；MinIO 使用 `latest`；应用服务没有健康检查、重启策略、资源限制和只读文件系统配置。

**风险**：热重载和宿主目录挂载降低稳定性；基础设施端口暴露扩大攻击面；浮动镜像导致不可复现；单机 Compose 缺少故障恢复和容量保护。

**验收标准**：拆分开发与生产 Compose/Helm；生产镜像固定版本并以非 root、只读根文件系统运行；仅网关暴露端口；配置健康检查、重启策略、CPU/内存限制、备份恢复和密钥注入。

### P1-01 viewer 可读取全量审计日志和模型配置元数据

动态验证：viewer 访问 `/api/audit` 和 `/api/models/configs` 均返回 200；用户管理和系统设置接口则正确返回 403。

审计日志可能暴露操作者、对象和行为轨迹；模型配置会暴露供应商、模型名、API 地址以及脱敏后的密钥结构。两者至少应限制为管理员/审计员，模型路由可另外提供只含业务能力状态的普通用户视图。

### P1-02 embedding 路由错误，RAG 实际处于关键词模式

当前 `embedding_model_id` 指向 MiniMax-M2.7 聊天模型；模型提供商为 `anthropic`，使用场景为空。知识库状态显示：73 个切片、`embedding_ready=false`、`retrieval_mode=keyword`、RAG 未启用。

页面已经提示“嵌入模型需支持 Embeddings 接口”，但保存路由时没有阻止聊天模型被选入 embedding 槽位。结果是知识问答可以工作，却只能使用关键词检索，语义召回质量和跨表述能力受限。

**验收标准**：模型配置显式声明能力（chat/embedding/rerank）；路由保存前进行能力探测；错误配置不可保存；切换模型后触发或提示增量重建；管理页显示向量维度、最近探测结果和失败原因。

### P1-03 仪表盘最近运行的数据源使用错误

后端已经提供 `/api/dashboard/recent-runs`，其中关联了 `quality_score`，前端 `Dashboard.vue` 却调用通用 `testRunApi.list()`。因此页面总体平均质量分为 84.0，但最近运行的质量分显示 `--`。

接口返回小写 `completed`，前端状态颜色映射只支持大写 `COMPLETED`；页面还直接显示 ISO 时间 `2026-09-19T14:59:51.721879`，没有使用统一中文时间格式。

**验收标准**：最近运行改用专用接口；统一状态枚举和展示文案；时间走统一格式化器；接口异常显示明确错误状态，不能静默退化成空数据。

### P1-04 移动端布局不可用

390px 视口下，仪表盘、项目列表、知识问答的文档宽度均为 556px。固定 192px 侧栏未切换为抽屉，知识问答在移动端只能看到历史会话栏，主聊天区被裁切。

**验收标准**：小于 768px 时侧栏改为抽屉；表格提供卡片/横向滚动策略；知识问答切换为会话列表与聊天页两级视图；关键页面在 390px 下不得产生页面级横向溢出。

### P1-05 可访问性和设计系统落地不完整

桌面页面虽然视觉一致，但每页仍有 1—4 个无可访问名称的交互元素；仪表盘、用例库、测试运行、报告、覆盖率、知识库和知识问答存在未关联标签的输入控件。项目工作区和用例库还检测到空名称按钮。

建议把按钮、图标、输入控件的 `aria-label`、`label`、焦点状态和键盘顺序纳入组件封装与前端自动检查，而不是逐页修补。

### P1-06 数据库演进采用 Alembic 与启动时 ALTER 双轨

仓库已有 14 个 Alembic 迁移，但 `backend/app/models/database.py` 仍包含大量启动时 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`、索引和约束修复。该方式让不同实例的结构演进难以审计，也会在多副本同时启动时产生锁和竞态风险。

**验收标准**：所有结构变化只通过版本化迁移执行；应用启动仅检查当前 schema revision，不再修改结构；上线流程先迁移、再滚动发布，并保留回滚预案。

### P1-07 可观测性、限流和容量治理缺失

代码中未发现 Prometheus/OpenTelemetry、统一 trace ID、模型 token/成本统计或实际的 API 限流实现。已有 `AI_RATE_LIMIT` 故障类型枚举，但尚未形成网关或应用限流能力。

企业运行至少需要：请求 ID 与运行 ID 贯通、结构化日志、任务队列积压指标、接口与模型延迟/错误率、模型 token 与费用、数据库/Redis/RabbitMQ 指标、告警规则和审计留存策略。

### P1-08 质量工程仍偏后端单元测试

GitHub Actions 只有 `backend-tests.yml`。前端仅有 `dev/build/preview`，没有 lint、单元测试、组件测试或端到端测试脚本。本轮代码扫描发现前端约 471 处 `: any`/`as any`，前后端约 330 处宽泛异常捕获或 `catch`；仪表盘的静默失败就是宽泛捕获导致问题不可见的实例。

建议建立后端测试、前端类型/lint、组件测试、API 契约测试、关键 E2E、镜像扫描和部署冒烟的分层流水线，并设置合并门禁。

## 4. 六种角色的使用结论

### 4.1 高级产品经理

**可用之处**

- 项目工作区已经提供概览、项目资料、测试计划、运行和质量入口，首次使用的路径比早期版本清晰。
- “智能用例生成”把需求文档和接口文档作为同级 Tab，符合两种常见输入来源。
- 用例生成后可以进入资产库、评审、计划和执行，已具备从需求到验证结果的基本追踪关系。
- 知识问答支持历史会话、新建会话、引用来源、项目范围和反馈，使用形态接近常见 AI 问答产品。

**欠缺之处**

- 全局模块和项目工作区同时存在，离开工作区后项目上下文容易丢失；覆盖率页面可选择到“电商验收源码”这类仅作为源码的数据项目，容易造成“功能没有数据”的误判。
- 缺少企业协作对象：组织、团队、项目成员、负责人、评审人、关注人、评论、通知订阅和待办中心。
- 缺少发布质量门禁的统一视图：某构建对应的需求、变更、用例、通过率、未关闭缺陷、覆盖率和最终准入结论没有聚合成一次 Release/Build 验收。
- 当前报告更偏单次运行结果，缺少跨版本对比、风险趋势、需求覆盖矩阵和可配置管理层视图。

### 4.2 高级软件测试工程师

**可用之处**

- PetClinic 与 E-Commerce 两个产品均能完成接口资产、用例、计划、运行、结果和报告的读取与核对。
- 两个基准运行均确实执行 1 条用例并产生 1 条结果，不能再认定为“零用例假成功”。
- 需求规则生成创建了 5 条草稿用例，每条均有 2—4 个步骤和非空预期结果。
- 针对单接口生成的 6 条用例都保留正确的 `endpoint_id`。
- 手工上传的覆盖率报告已经可以与测试运行关联：示例报告行覆盖率 78.4%、分支覆盖率 62.5%、151/193 行。
- 定时任务初始暂停状态和“每天凌晨两点”Cron 均正确。

**欠缺之处**

- 运行成功标准仍需要更严格：零用例、全部跳过、环境不可达、报告未生成、覆盖率缺失应分别形成明确状态和门禁结果。
- 用例版本、计划版本、环境版本已有部分快照，但还需在 UI 中完整展示“本次运行究竟使用了什么”，并支持一键复跑同一快照。
- 缺少数据驱动参数集、前后置数据清理、共享变量作用域、失败重试策略、断言模板库和 Mock/虚拟服务的成熟管理体验。
- 缺陷与外部研发系统尚未形成稳定双向同步、去重、状态回写和失败补偿。
- 覆盖率自动采集对 Java 常驻服务已有设计和 Agent 入口，但企业 CI/CD 自动接入、构建产物匹配、探针状态和失败诊断仍属于后续能力。

### 4.3 软件开发工程师

**可用之处**

- 后端模块边界覆盖项目、文档、用例、执行、报告、缺陷、覆盖率、知识库和模型路由，功能扩展点较完整。
- 执行链路已有环境 revision、运行 snapshot、触发上下文和异步任务。
- 知识问答的会话、消息、反馈和来源字段已持久化，且会话按用户隔离。
- 当前后端测试在同一提交上已有 103 项通过记录，前端生产构建通过。

**欠缺之处**

- 认证依赖没有在路由层统一施加，导致新增模块很容易忘记鉴权。应改为“默认拒绝 + 明确公开”的路由策略。
- 前端大量 `any` 降低接口变更的编译期发现能力；应从 API response DTO、状态枚举和核心页面开始消除。
- 宽泛异常捕获与静默处理会隐藏线上问题；需要统一错误码、用户错误态、日志上下文和可重试策略。
- 31 个 API 模块和 213 个路由已经具有一定规模，应生成并检查 OpenAPI 契约，避免请求字段变更后脚本和前端悄然失配。

### 4.4 高级架构师

**可用之处**

- PostgreSQL、Redis、RabbitMQ、MinIO、FastAPI、Celery、Vue 的职责划分合理，适合当前阶段快速演进。
- 生产 Compose 已主动避免挂载 Docker Socket，说明执行隔离风险已被识别。
- 运行快照、环境版本和覆盖率 Agent 为后续 Runner 解耦奠定了基础。

**欠缺之处**

- 缺少组织/租户边界和统一授权服务，无法安全地承载多团队。
- 单机 Compose 仍是开发形态；没有网关、TLS、服务发现、弹性伸缩、备份恢复、灾难演练和多可用区设计。
- Celery worker 同时承载平台逻辑与测试执行，应进一步拆成控制面与隔离 Runner；Runner 需要任务级网络策略、资源配额、临时凭证、工作区销毁和制品签名。
- 数据库迁移双轨、浮动镜像和源码挂载影响发布确定性。
- 缺少端到端可观测性，无法快速回答“一次失败是平台、模型、队列、环境还是被测服务导致”。

### 4.5 UI/UX 设计系统总监

**可用之处**

- 15 个桌面页面视觉语言较统一，均未产生桌面横向溢出和浏览器控制台错误。
- 项目概览中的就绪度、快捷操作和上下文 Tab 能帮助新用户理解下一步。
- 知识问答的左侧会话、右侧对话、来源引用和空状态已经形成清晰的信息架构。
- 覆盖率无数据状态能够解释支持的采集方式和下一步操作。

**欠缺之处**

- 移动端三个核心页面全部溢出，属于阻断级体验问题。
- 仪表盘直接显示 `completed`、原始 ISO 时间和 `--` 质量分，削弱数据可信度。
- “智能用例生成”顶栏与正文标题重复；“使用 AI / 仅规则 / AI 结构化”等术语没有解释决策差异。
- 全局项目选择器没有区分业务项目、源码项目及其可用能力，容易进入无数据状态。
- 输入标签、图标按钮名称、键盘操作和焦点样式没有成为设计系统组件的强制规范。

### 4.6 AI Agent 开发工程师

**可用之处**

- 支持模型配置与按场景路由，AI 已用于需求解析、用例生成、脚本生成、缺陷分析、报告分析和知识问答。
- 知识问答采用“无命中拒答”，返回来源，保留最近 10 条对话消息，并用最近问题补全追问检索语义。
- 本轮对“泄露系统提示词、API Key、数据库密码”的注入问题进行了验证，模型没有输出检测到的敏感值，并给出了拒绝性回答。
- 脚本生成动态验证成功，返回有效脚本，说明历史 coroutine 500 问题已修复。

**欠缺之处**

- 当前主要是多个单次 LLM 调用，还没有统一 Agent 运行时：缺少计划、工具注册与权限、状态机、可暂停/恢复、人工审批、预算、重放和步骤级追踪。
- 没有 prompt 版本、模型实际版本、输入/输出 token、费用、缓存命中、延迟、重试、失败分类和 trace ID 的持久化治理。
- 缺少离线评测集与发布门禁，无法量化比较模型或提示词变更对解析准确率、用例有效率、引用正确率和幻觉率的影响。
- RAG 未启用语义检索；现有上下文虽限制长度，但没有把检索内容明确当作不可信数据进行指令隔离，也没有输出引用一致性校验。
- 高风险工具动作需要明确的人机协同策略，例如执行 SQL、创建大量用例、修改定时任务、触发真实环境测试、创建外部缺陷。

## 6. 建议实施顺序

### 第一批：上线阻断项（建议立即处理）

1. 建立全局 API 认证基线，只对白名单路由公开；修复定时任务、脚本、报告、仪表盘、运行结果、数据源等接口。
2. 建立资源级授权函数，先覆盖项目、用例、计划、运行、报告、缺陷、知识库、审计和模型配置；viewer 不得读取审计与模型配置。
3. 增加匿名、角色、跨项目权限矩阵自动化测试，并放入 CI。
4. 拆出生产部署配置，关闭 reload 和源码挂载，收口端口，固定镜像，增加健康检查、重启和资源限制。

### 第二批：数据可信与核心体验（第一批完成后）

1. 修复仪表盘最近运行数据源、状态本地化、时间格式和错误态。
2. 为模型增加能力声明与路由校验，配置真正的 embedding 模型并完成知识库重建。
3. 修复移动端导航、知识问答和表格布局；补齐输入与图标按钮的无障碍名称。
4. 将项目类型与可用能力显式化，减少源码项目、测试项目、被测服务之间的选择混淆。

### 第三批：企业控制面（建议 1—2 个迭代）

1. 建立组织、团队、项目成员和项目角色模型，完成数据迁移和全资源隔离。
2. 统一 Alembic 迁移，移除启动时改表。
3. 引入网关限流、密钥管理、SSO/OIDC、结构化日志、指标、Trace、告警与备份恢复演练。
4. 完善前后端质量流水线和 API 契约门禁，减少 `any` 与静默异常。

### 第四批：AI Agent 与 CI/CD 深化

1. 建立统一 AI 调用账本：prompt/模型版本、token、费用、延迟、重试、来源、输出与用户反馈。
2. 建立评测数据集和 AI 变更门禁，先覆盖需求解析、用例生成和知识问答三条高价值链路。
3. 引入受控 Agent 工具协议、动作权限、预算与人工审批；高风险动作默认等待批准。
4. 将 Jenkins 构建、部署环境、测试计划、测试结果、缺陷和覆盖率聚合为 Build/Release 质量门禁。

## 7. 企业试点建议

在第一批安全问题修复前，平台只应放在隔离网络中，由可信测试人员使用，不应暴露到办公网之外，也不应存放生产密钥或敏感接口数据。

第一批完成并通过权限矩阵验收后，可选择一个非核心业务、一个测试团队、两个环境做 4—6 周试点。试点应跟踪：用例生成采纳率、人工修改率、执行稳定率、缺陷有效率、平均定位时间、模型调用成本、知识问答引用正确率和平台自身故障率。达到约定指标后，再推进多团队和 CI/CD 门禁接入。
