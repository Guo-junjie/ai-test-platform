## 0. 给 AI 执行者的使用说明（先读这一节）

### 0.1 你要做什么（一句话）

把已经做得扎实、但彼此串不起来的 **36 个功能页**，按 `docs/frontend-redesign-demo.html`（30 屏）重构成**一条业务测试人员能自助走完的主链路**：以项目工作区为唯一主入口、每个分区都有内联数据、一切技术参数改为选择器、任何跳转不丢项目上下文。

**改造性质**：前端重构 + 少量新建视图。**不改后端契约、不改视觉语言、不改 `docker-compose.yml`。**

### 0.2 执行顺序（不可颠倒）

```
① 先读「第二部分 · 技术 0 约束」——违反即视为改造失败
② 按「技术 7 任务分解」的 4 个批次推进，每批结束跑「技术 8 技术验收门槛」
③ 每屏改造前对照「第一部分 · 产品 6 30 屏逐屏体验验收标准」逐条自检
④ 每屏改造前先看「技术 5 逐屏改造规格」的「必须消除」清单
```

### 0.3 五条最易踩坑的提醒

| # | 提醒 | 说明 |
|---|---|---|
| 1 | **不要新增或臆造后端接口** | 页面数据一律取自已存在接口；接口缺失时按「技术 6 接口缺口」给前端降级 + 可读空态，**不得**阻塞交付或伪造数据 |
| 2 | **不要改 `theme.css` 已有令牌值** | 只允许新增 `--app-*` 语义令牌；视觉语言冻结在 v1「清透白」 |
| 3 | **技术参数一律改选择器** | cron 表达式、JSON 断言、commit SHA、UUID、端口、令牌变量名、连接串、IP 段、报告/结果 ID、审计 `action` 代码串——**全部**改为下拉或可视化选择器（这是本次改造的核心命题） |
| 4 | **同一个东西只在一处渲染** | 测试计划、运行记录都存在「两套 CRUD / 三处渲染」，必须按「技术 2.3 单轨化决策」收敛 |
| 5 | **跳转参数键统一为 `project_id`** | 禁止 `id`；硬编码 hash 路由（`href="/#/..."`）数量必须为 0 |

### 0.4 关于本文档的编号

第一、二部分各自内部编号（如「产品 5.1」「技术 2.3」）；正文中出现的 `§x.y` 均指**所在部分内部**的章节号。跨部分引用一律写明「产品 x」或「技术 x」。

### 0.5 词汇表（避免理解偏差）

| 术语 | 含义 |
|---|---|
| **工作区** | 项目工作区 = `/projects/:id/*`，改造后含 8 个分区（概览/用例/测试计划/执行记录/质量结果/环境/成员/设置） |

## 产品 1. 改造目标与成功指标

### 1.1 一句话目标

**把已经做得扎实、但彼此串不起来的 36 个功能页，收敛成一条「业务测试人员能自助走完」的主链路**：以项目工作区为唯一主入口、每个分区都有内联数据、一切技术参数改为选择器、任何跳转不丢项目上下文。

评估报告的判断可直接引用为目标依据：当前是「能力密度远高于串联密度」的平台，主链路上存在**失效指引 / 手写 JSON / 上下文丢失**三类反复出现的断点（评估报告 §0）。

### 1.2 成功指标（可量化，含口径）

| # | 指标 | 定义与口径 | 当前基线 | 目标值 | 测量方式 |
|---|---|---|---|---|---|
| M1 | 首任务完成率 | 「新用户从 0 到第一次成功执行一次测试计划」在可用性测试中完成的人数占比 | **待埋点**（评估报告仅给建议阈值，无实测值） | ≥ 85% | 5 人走廊测试（评估报告 §7）；Nielsen：5 人可发现约 85% 可用性问题 |
| M2 | 首任务耗时**中位数** | 同 M1 任务，从登录到看见运行结果的耗时**中位数**（用中位数，不用均值，避长尾干扰） | **待埋点** | ≤ 15 分钟 | 可用性测试计时 |
| M3 | 断言自助完成率 | `tester` 角色**独立**完成「生成 → 补断言 → 提交评审」的人数占比 | **待埋点** | ≥ 85% | 可用性测试（评估报告 UX-P0-4 验证指标） |
| M4 | 手写技术参数界面数 | 源码中存在「要求用户手写 JSON / cron / SHA / UUID / 端口 / 令牌变量名 / 连接串」输入位的界面数 | **11**（评估报告 §2.2 UX-P1-3 表格共 11 行） | ≤ 3 | 源码 grep + 人工复核（评估报告 UX-P1-3 验证指标） |
| M5 | 工作区跳转上下文携带率 | 从项目工作区离开的跳转中，URL 携带 `project_id` 的比例 | **非 100%**（`ProjectQuality.vue:30,33` 两张卡丢失；`SourceManage.vue:366-368` 误用键 `id`） | 100% | 源码审查 + E2E 断言 |

> **护栏指标（不得回退，非本轮提升目标）**：有列表的视图分页覆盖率（基线 9/36 ≈ 25% → 目标 100%）、空 `catch` 数（基线多处 → 目标 0）、状态/触发器中文词典重复定义处数（基线 ≥ 5 处 → 目标 1）、响应式关键页在 1280px / 768px 无页面级横向溢出（基线含 `@media` 视图 5/36 ≈ 14%）、生产构建产物中演示口令字符串命中数（基线 1 → 目标 0）。

**口径纪律**：所有涉及「耗时」的指标一律取**中位数**；所有「完成率」均以**可用性测试任务**为口径，不是页面点击率；无实测的基线一律标注「待埋点」，禁止用估算值冒充基线。

### 3.3 全局页 vs 项目工作区：职责划分原则

**核心原则：同一实体只在一处渲染。** 全局页定位为「跨项目总览 / 跨项目操作」，工作区为「项目内操作」；同一份数据的**主渲染位置唯一**。

**现状问题证据**（评估报告 §4.2 问题 2）：

| 实体 | 现状全局入口 | 现状工作区入口 | 后果 |
|---|---|---|---|
| **测试计划** | `TestRun.vue` 的「管理计划」抽屉 | `workspace/ProjectPlans.vue` | 同一实体**两套 CRUD 界面** |
| **运行记录** | `TestRun.vue:138-219` | `ProjectOverview.vue:29-48` + `ProjectRuns.vue:39-87` | **同一份 run 数据在 3 处渲染**，状态映射字典各写一份 |
| **质量数据** | `/report`、`/defects`、`/coverage`、`/quality-trend` | `ProjectQuality.vue:29-34`（4 张零数据跳转卡） | 工作区只有跳转卡、无内联数据 |

**改造后职责表**

| 实体 | 工作区（项目内主入口） | 全局页（跨项目总览） | 主渲染位置 |
|---|---|---|---|
| 测试计划 | 工作区「测试计划」tab：项目内计划 CRUD + 执行入口 | API 计划执行页：**跨项目计划总览**，不再承载项目内 CRUD | 工作区（项目内） |
| 运行记录 | 工作区「执行记录」tab | API 计划执行页：跨项目运行总览 | 工作区；全局页按项目聚合只读视图 |
| 质量结果 | 工作区「质量结果」tab：**内联**通过率/缺陷分布/覆盖率摘要 | 测试报告 / 缺陷中心 / 覆盖率 / 趋势：跨项目视图 | 两者各有定位，**数据卡片内容不同**，不做同一张卡的重复渲染 |
| 环境 | 工作区「环境」tab（新增） | 无独立全局页 | 工作区 |

**四条硬性原则**（评估报告 §4.3，作为本改造的验收铁律）：
1. 每个 tab 必须有**内联数据**——不允许「纯跳转卡页」；
2. 任何**离开工作区的跳转**都必须携带 `project_id`；
3. **同一实体只在一处渲染**——全局页 = 跨项目总览，工作区 = 项目内操作；
4. 侧栏 label 与路由标题**同源**。

## 产品 7. 全站关键体验原则（贯穿性硬性要求）

> 逐条可检查；每条一句话。「工作区」= 项目工作区 8 个分区。

1. **工作区每个 tab 必须有内联数据**——不得是零数据跳转卡；首屏至少 3 张非空数据卡。
2. **离开项目工作区的任何跳转必须携带 `project_id`**；参数键统一为 `project_id`（与后端 `access_policy.py` 资源键一致），不得使用 `id` 等其他键名。
3. **前端源码中跳转携带项目的参数键唯一**；硬编码 hash 路由（如 `href="/#/..."`）数量为 0。
4. **一切技术参数改为下拉或可视化选择器，不得手写**：cron 表达式、JSON 断言、commit SHA、UUID、端口、令牌变量名 / 密钥、连接串、IP 段、报告/结果 ID、审计 `action` 代码串。
5. **空态必须包含引导说明与一个可执行操作**——不允许只有默认文案的空态。
6. **表格必须带分页器**（`el-pagination` 或等价分页控件），无例外。
7. **同一实体只在一处渲染**——测试计划仅工作区一套 CRUD；运行记录主渲染位置唯一。
8. **删除 / 归档类动作必须可恢复且有二次确认**，并在确认文案中说明影响范围。
9. **状态 / 触发器 / 用例状态 / 缺陷严重度使用单一中文词典**，全站同状态同文案（重复定义处数 = 1）。
10. **错误态必须可区分「无数据」与「接口异常」**，并含局部重试入口；前端空 `catch` 块数量为 0。
11. **侧栏 label 与路由标题同源生成**，不得两处分别维护。
12. **进入任一层级页面必须能得知「我在哪个项目 / 哪一层」**——恢复面包屑或等价位置提示。
13. **生产构建产物中不得出现任何演示账号口令字符串**。
14. **仅用键盘可完成「登录 → 建项目 → 执行计划」全流程**，且焦点可见（`:focus-visible` 有效）。
15. **所有输入 / 下拉 / 图标按钮具备可访问名**（可见 label 或 `aria-label`）。
16. **关键页在 1280px 与 768px 下无页面级横向溢出**；宽表采用「重要列固定 + 其余横向滚动」或小屏切卡片。
17. **主链路上的引导必须可点击且指向真实存在的页面/分区**——不得出现指向不存在位置的提示文案。
18. **页面顶部不使用大段文字教程**——改为 1 行摘要 +「查看流程」折叠面板或「下一步」按钮（不引入新手引导蒙层，见 R-14）。

## 技术 1. 总体改造策略

### 1.1 分层顺序

改造严格按**五层顺序**推进，下层完成并通过验收点后上层才能开始；同层内可并行。

```
① 令牌层（只读基线）  →  ② 布局层（Layout / 导航 / 面包屑）
   →  ③ 路由层（IA 重组 + 新增路由）  →  ④ 组件层（公共组件抽取）
   →  ⑤ 视图层（逐屏改造）
```

| 层 | 做什么 | 为什么这个位置 | 验收点 |
|---|---|---|---|
| ① 令牌层 | **不动**。仅登记 `theme.css` 已有令牌清单；如需新组件，新增语义令牌（不改旧值） | 视觉语言冻结，避免"改结构顺带改配色" | `git diff theme.css` 仅新增 `--app-*`，无删除 / 无改值；`npm run build` 通过 |
| ② 布局层 | 重构 `Layout.vue`：侧栏按原型 `NAV` 重组为 7 组 + 头像菜单个人域；顶栏恢复面包屑 + 全局搜索占位 + 通知铃；新增"项目上下文侧栏"模式 | 导航与面包屑是全局框架，先定型，后续每屏的 `meta.title` 与侧栏 label 才能同源 | 侧栏项与原型 `NAV` 逐项对应；切换项目后侧栏切换为项目内导航；面包屑在 `/projects/:id/*` 下正确渲染 |
| ③ 路由层 | 重组 `router/index.ts`：新增 `/runs`、`/runs/:id`、`/case-assert`、项目工作区 8 个子路由；修正 `meta.title` 与侧栏同源 | 路由是视图挂载点，组件与视图改造都依赖稳定路由 | 30 屏**每屏可达**且深链可用；`meta.title` 与侧栏 label 一致；无死链 |
| ④ 组件层 | 抽取公共组件（见技术 4），先组件后页面 | 视图改造大量复用组件，先建契约可避免逐屏手写重复结构 | 组件 props/emits 契约冻结；组件可独立渲染（Story 或独立页手测） |
| ⑤ 视图层 | 逐屏改造（见技术 5） | 最后做，使每屏只做"组装"，降低返工 | 每屏消除对应问题清单项；无手写技术参数；空态 + 错误态齐备 |

### 1.2 为什么是这个顺序

- **令牌层先冻结**：原型已把 v1 令牌验证到 30 屏，任何配色改动都会引发大面积回归，冻结是成本最低的保护。
- **布局层先于路由层**：侧栏 / 面包屑依赖路由 `meta`，但两者必须同源生成；先把 Layout 的数据驱动方式定下（从 `NAV` 常量渲染），路由只需补 `meta.title`。
- **路由层先于组件层**：`/projects/:id/environments` 等新路由是组件落点，路由不确定则组件无处挂载。
- **组件层先于视图层**：`StructuredAssertBuilder` / `SchedulePicker` 等是多次复用的核心交互，先建契约、后装配页面，避免"边做页面边改组件签名"。
