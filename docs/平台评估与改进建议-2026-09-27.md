## 0. 结论摘要

**一句话判断：这是一个"能力密度"远高于"串联密度"的平台。**

单个功能页面普遍做得相当扎实——执行页有步骤条与事件时间线、覆盖率的采集方式说明到位、缺陷页有四级过滤与状态流转、模型配置有能力声明与双重校验。但把这些页面**串成一条用户能顺畅走完的路**这件事，尚未系统性地做过：主链路上存在失效指引、手写 JSON、上下文丢失三类反复出现的断点。

| 视角 | 判断 | 依据 |
|---|---|---|
| **最终用户** | 能完成，但不顺手 | 主流程可走通，但每跨一步都可能丢项目上下文、撞上手写技术参数、或撞上一条指不到地方去的引导 |
| **产品经理** | 可受控试点，不可规模化 | 单团队单项目试点成立；多部门协作、生产级运维与发布准入三块控制面缺失或薄弱 |

**能力成熟度自评（依据源码实现深度，非功能数量）**

| 维度 | 评分（5 分制） | 依据 |
|---|---:|---|
| 测试能力完整度 | 3.8 | 代码解析 8 框架适配器、用例生成、场景编排、脚本生成、三类执行、覆盖率（含 JaCoCo 手写 TCP 协议）、缺陷 AI 根因、双模式报告、RAG 知识库——均为真实实现 |
| 功能使用便捷性 | 2.3 | 主链路 5 阶段 7 处断点；9 类界面仍要求用户手写 JSON / cron / SHA / UUID / 端口 |
| 信息架构与串联 | 2.2 | 侧栏分类维度混装；全局页与项目工作区双轨并存；同一实体在三处渲染 |
| 企业协作能力 | 1.8 | 无组织/团队/租户层，无 SSO，无评论/评审人/关注人/待办中心 |
| 部署与运维成熟度 | 3.2 | 已有硬化生产编排，但默认路径与文档脱节，迁移双轨未除 |
| 安全与合规基线 | 3.5 | 全局默认拒绝鉴权 + 资源级授权已成型；但默认交付物的密钥与凭据治理存在实质漏洞 |
| 可观测与治理 | 1.5 | 无限流、无指标端点、无 traceId、无模型成本账本、无发布级门禁聚合 |
| **综合** | **2.7 / 5** | 可受控试点，不能直接作为企业生产级质量平台 |

## 2. 视角一：现有功能的使用便捷性与体验痛点

### 2.1 P0 · 阻断级（严重度 3–4）

#### UX-P0-1【严重度 4】就绪度引导指向一个不存在的位置

| 项 | 内容 |
|---|---|
| **证据** | `ProjectOverview.vue:144-146` 在"项目就绪度"卡片中对"已发布环境"这一项给出提示：**「到「测试上下文 → 环境」创建并发布」**。但 `ProjectContext.vue` 全文只有 4 张解析入口卡（接口文档生成 / 需求文档生成 / 代码解析 / 接口文档评审）+ 一段"代码版本"表格，**不存在任何环境分区**。工作区的 tab 定义见 `ProjectWorkspace.vue:26-31`：概览 / 测试上下文 / 测试计划 / 运行中心 / 质量结果——**没有环境**。环境的真实入口在 `Projects.vue:249-290`（项目详情**抽屉**内的"测试环境"表格 + 新建/健康检查/发布）。 |
| **违反原则** | Nielsen #2 系统与现实匹配、#10 帮助与文档 |
| **影响** | "项目就绪度"是新用户最依赖的引导组件，它给出的路径点不到。用户会反复在"测试上下文"里找环境，最终放弃或转向文档。这是**首个使用会话就会遇到的挫败点**。 |
| **改进方向** | 二选一，建议 A：<br>**A（推荐）** 新增工作区分区「测试环境」（路由 `/projects/:id/environments`），把 `Projects.vue:249-290` 的环境表格与新建/健康检查/发布逻辑抽成 `components/EnvironmentPanel.vue`，工作区与项目详情两处复用。执行的前置条件是环境，它属于项目内高频路径，不应藏在低频的详情抽屉里。<br>**B（最小改动）** 把 `ProjectOverview.vue:145` 的提示改为**可点击动作链接**，指向"项目管理 → 项目详情 → 测试环境"，并同步修正 `TestRun.vue:95` 的同类文案。 |
| **验证指标** | 新用户"从 0 到发布第一个环境"任务完成率 ≥ 90%；任务耗时中位数 ≤ 3 分钟（用中位数而非均值，避免长尾干扰）。 |

#### UX-P0-2【严重度 4】默认交付物会在登录页公示管理员账号密码

| 项 | 内容 |
|---|---|
| **证据** | ① `Login.vue:94` 无条件渲染 `<p class="form-hint">默认管理员账户：admin · Admin123</p>`——**没有 APP_ENV / APP_DEBUG 条件判断**；<br>② `modules/auth/auth_service.py:286-292` 硬编码 5 个演示账号明文口令（`superadmin/SuperAdmin123`、`admin/Admin123`、`tester/Tester123`、`developer/Developer123`、`viewer/Viewer123`），`:333-343` 在**非生产环境**且 users 表为空时**自动种子这些账号**，`:370-381` 兜底路径还会再建一个 `superadmin/SuperAdmin123`；<br>③ `config.py:15` `APP_ENV` 默认 `development`、`:16` `APP_DEBUG` 默认 `true`；<br>④ `docker-compose.yml:110` 的 backend 以 `uvicorn --reload` 启动，`.env:57-58` 为 `APP_ENV=development` / `APP_DEBUG=true`。 |

#### UX-P0-4【严重度 3】断言与请求体仍需手写 JSON，业务测试人员无法自助

| 项 | 内容 |
|---|---|
| **证据** | `CaseLibrary.vue:148` `<el-input v-model="editForm.request_json" type="textarea" :rows="5" placeholder="JSON">`、`:151` 的 `expected_json` 同样是裸 textarea；`:601-602` 回填时 `JSON.stringify(..., null, 2)`；`:611-614` 保存时 `JSON.parse` 失败即弹"请求数据 / 预期结果 必须是合法 JSON"。 |

| **改进方向** | 断言构造器（UI 优先、JSON 兜底）：<br>· **请求体**：从接口资产的 `endpoint` schema 生成表单化字段编辑器（字段名 + 类型 + 值），支持"切到高级 JSON 模式"；<br>· **断言**：结构化行编辑 `[字段路径] [操作符: == / != / > / < / contains / 正则 / JSONPath] [期望值]`；内置断言模板库（HTTP 200、字段存在、响应时间 < N ms、Schema 校验）；<br>· JSON 作为**只读产物**展示并可复制，不再作为唯一输入；<br>· 断言库支持"插入模板"而非从零填写。 |
| **验证指标** | `tester` 角色独立完成"生成 → 补断言 → 提交评审"的任务完成率 ≥ 85%；因 JSON 语法错误导致保存失败的次数降为 0。 |

| **无批量导出** | 全仓无 `to_csv` / `openpyxl` / 导出端点 | 用例、缺陷、结果、报告明细支持导出 CSV/Excel（企业交付与审计的常规要求） |
| **通知渠道不全** | `modules/notification/notifier.py:82-89` 仅通用 webhook + 钉钉 + SMTP | 补企业微信 / 飞书机器人，以及自定义出站事件与重试 |
| **构建日志入库** | `git ls-files` 确认 `frontend/npm_install.log`、`frontend/vite_build.log` **被版本控制跟踪** | 从索引移除并补进 `.gitignore` |

### 3.3 凭据与密钥治理缺口（独立发现）

这是我在核查交付物时发现的、**会直接影响"能否对外部署"判断**的一组问题：

| 问题 | 证据 | 风险 |
|---|---|---|
| **`.env` 被纳入版本控制** | `git ls-files` 输出包含 `.env`。`.gitignore:4` 虽列了 `.env`，但 gitignore 无法反跟踪已入库文件 | 仓库分发即等同于分发了基础设施口令 |
| **基础设施口令复用且弱** | `.env:3` `POSTGRES_PASSWORD`、`:15` `RABBITMQ_PASSWORD`、`:21` `MINIO_ROOT_PASSWORD`、`:24` `MINIO_SECRET_KEY` 全部为同一个 `aitp_secret_2026`；`.env:11` `REDIS_PASSWORD=` **为空** | 一处泄露即数据库、消息队列、对象存储全线失守；Redis 无密码 |
| **JWT 签名密钥是可公开猜测的占位串，且能绕过启动校验** | `.env:53` `SECRET_KEY=change-this-to-a-random-secret-key-in-production`；`config.py:29` 的校验条件是 `len < 32` **或** 等于 `"dev-secret-key-change-in-production"`——该占位串长 49 字符且不等于默认串，**两条校验都不触发**；而 `auth_service.py:70` 正是用它以 HS256 签发 JWT | 知道该串的人可自行伪造任意用户（含 super_admin）的 token。**这是鉴权链上的实质漏洞** |
| **AES 密钥同样是可公开猜测的占位串，同样绕过校验** | `.env:54` `AES_ENCRYPTION_KEY=change-this-to-a-32-byte-hex-key`（恰好 32 字符）；`config.py:31` 的校验条件是等于 `"0" * 32` **或** `len < 32`——两条都不触发；`utils/crypto.py:36` 用它加密数据库连接凭据、仓库 Token 等 | 数据库中所有"加密"字段可被离线解密 |
| **登录页公示默认凭据** | `Login.vue:94` | 见 UX-P0-2 |

| 项 | 内容 |
|---|---|
| **影响** | 这四项叠加后，一个按 README 部署、把端口映射到办公网的实例，实际上处于"JWT 可伪造 + 凭据可解密 + 默认管理员口令公开"的状态。`config.py` 的 `validate_production()` 设计意图正确，但**校验名单是按具体字面量枚举的，而 `.env` 里的占位串恰好不在名单内**——校验被自己的占位值绕过了。 |
| **改进方向** | ① **立即**：`git rm --cached .env`，轮换 Postgres / RabbitMQ / MinIO 口令，给 Redis 设密码；<br>② `.env.example` 入库（占位值改为明显的 `CHANGE_ME`），`.env` 保持在忽略列表；<br>③ 把 `validate_production()` 从"字面量黑名单"改为**模式校验**：拒绝包含 `change-this` / `dev-` / `CHANGE_ME` / 连续相同字符等特征的值，并强制与 `.env.example` 的占位值不同；<br>④ 生产环境密钥从 Secret Store 注入（Docker secrets / Vault / K8s Secret），代码内不保留默认值；<br>⑤ 增加启动自检报告：打印"密钥是否已轮换"的显式结论。 |
| **验证指标** | `validate_production()` 对 `.env.example` 中的每个占位值都能拒绝；启动日志中密钥轮换状态可见；仓库中 `git ls-files` 不再包含 `.env`。 |

## 4. 视角三：排版、信息架构与模块串联逻辑

### 4.1 当前导航结构

```
顶栏   折叠按钮 │ 页面标题（单行，无面包屑）           │ 风格切换 · 通知铃 · 用户菜单
侧栏   工作台
       项目
       测试中心 ── 智能用例生成 / 用例管理与评审 / API 计划执行 / 定时任务 / 场景编排 / 脚本生成 / 数据库连接
       质量中心 ── 测试报告 / 报告分析 / 缺陷中心 / 代码覆盖率 / 质量趋势
       知识中心 ── 知识库 / 知识问答
       解析与集成 ─ 代码解析 · 接口文档评审 · 仓库配置
       系统 ────── 用户管理 / 消息通知 / 基础配置 / AI 模型配置 / 质量门禁 / 审计日志 / 个人设置
       （共 6 组 26 项；来源：Layout.vue:22-104）
```

### 4.2 结构性问题（4 类）

**问题 1｜同级菜单项不属于同一分类维度（违反 Nielsen #4 一致性与标准）**

| 组 | 混装内容 |
|---|---|
| 测试中心 | 资产（用例管理与评审）+ 创作（智能用例生成 / 场景编排 / 脚本生成）+ 执行（API 计划执行 / 定时任务）+ 配置（数据库连接） |
| 系统 | 个人域（个人设置 / 消息通知）+ 管理域（用户管理 / 基础配置 / AI 模型配置 / 质量门禁 / 审计日志） |

另外：「质量门禁」被放在「系统」下（`Layout.vue:101`），而「质量趋势」在「质量中心」（`:60`）——两个同属质量域的模块分居两组。

**问题 2｜全局页与项目工作区双轨并存，形成"同一实体多处渲染"**

| 实体 | 全局入口 | 工作区入口 | 后果 |
|---|---|---|---|
| 测试计划 | `TestRun.vue` 的"管理计划"抽屉（`:48`） | `workspace/ProjectPlans.vue` | 同一实体两套 CRUD 界面 |
| 运行记录 | `TestRun.vue:138-219` | `ProjectOverview.vue:29-48` + `ProjectRuns.vue:39-87` | **同一份 run 数据在三处渲染**，状态映射字典各写一份 |
| 质量数据 | `/report`、`/defects`、`/coverage`、`/quality-trend` | `ProjectQuality.vue:29-34` | 工作区只有跳转卡，无内联数据（见 UX-P1-1） |

**问题 3｜工作区分区与内容不匹配，"测试上下文"名不副实**

`ProjectWorkspace.vue:26-31` 的 5 个 tab 中，"测试上下文"（`ProjectContext.vue`）实际只包含 4 张解析入口卡 + 代码版本表；而"环境"这个执行的必要前置条件**不在工作区任何 tab 内**，只在 `Projects.vue` 的详情抽屉里。这直接导致 UX-P0-1 的失效指引。

**问题 4｜无层级提示**

`Layout.vue:117` 明确移除了面包屑，header 只显示当前页 title。用户进入 `/projects/:id/plans` 时无法从界面上得知自己在哪个项目、处于哪一层。

### 4.3 目标形态（建议按用户任务流重组）

| 阶段（JTBD 陈述） | 归属 | 收敛后的入口 |
|---|---|---|
| 当我接手一个项目时，我想要**接入代码与文档**，以便平台了解被测对象 | 项目工作区 · 测试上下文 | 代码版本、接口文档、需求文档、**环境（从详情抽屉迁入）** |
| 当我要准备测试时，我想要**产出并评审用例**，以便有可执行的资产 | 项目工作区 · 测试资产（或全局"测试资产"） | 智能用例生成、用例库、场景编排、脚本生成、数据库连接 |
| 当我要组织回归时，我想要**选择用例并固化版本**，以便结果可复现 | 项目工作区 · 测试计划 | 计划 CRUD、**用例勾选（含权重/tag）**、发布不可变 revision |
| 当我要验证时，我想要**执行并观察过程**，以便定位问题 | 项目工作区 · 运行中心 + 全局"执行与调度" | 计划执行、定时任务、**运行详情就地抽屉** |
| 当我要出结论时，我想要**看到质量态势**，以便做发布决策 | 项目工作区 · 质量结果 + 全局"质量" | 报告、缺陷、覆盖率、质量门禁、趋势（**全部带 project_id**） |
| 当我遇到问题时，我想要**查企业知识**，以便复用经验 | 知识中心 | 知识库、知识问答 |
| 当我要管理平台时，我想要**配置与治理**，以便合规可用 | 系统管理（右上角用户菜单承载个人域） | 用户、基础配置、AI 模型、审计 |

**四条硬性原则**：
1. **每个 tab 必须有内联数据**——不允许"纯跳转卡页"；
2. **任何离开工作区的跳转都必须携带 `project_id`**；
3. **同一实体只在一处渲染**——全局页定位为"跨项目总览"，工作区为"项目内操作"；
4. **侧栏 label 与路由标题同源**——杜绝两处维护导致的命名漂移。

## 7. 试点建议与跟踪指标

1. **第 1 批完成前**：平台只应部署在隔离网络内，由可信测试人员使用；不应暴露到办公网之外，不应存放生产密钥或真实敏感接口数据。理由见 §3.3。
2. **第 1 批完成并通过验收后**：可选择一个非核心业务、一个测试团队、两个环境做 **4–6 周试点**。
3. **试点应跟踪的指标（HEART / GSM 落地）**：

| 维度 | 指标 | 目标基线 |
|---|---|---|
| Task success | "从 0 到第一次成功执行计划"的任务完成率 | ≥ 85% |
| Task success | 该任务耗时**中位数**（不用均值，避长尾干扰） | ≤ 15 分钟 |
| Engagement | 周活跃测试人员 / 被授权人数 | ≥ 70% |
| Retention | 次周回访率 W2/W1 | ≥ 60% |
| Adoption | AI 生成用例采纳率（adopted / generated） | ≥ 40% |
| Happiness | 平台 NPS（推荐意愿，不等同满意度 CSAT） | ≥ 30 |
| Quality | 平台自身故障率（Run 失败中平台侧原因占比） | ≤ 5% |
| 成本 | 单次完整回归的模型 token 消耗与折算费用 | 建立基线后逐季下降 |

4. 达到约定指标后，再推进**多团队接入**与 **CI/CD 发布门禁**。
