# 用例评审任务交付说明

## 改造目标

原有评审只在用例上保存 `review_state`，没有评审任务、指定评审人和评审版本。改造后，每次提交都会创建独立评审任务，绑定提交时的不可变用例版本，并为每位评审人建立个人待办和结论记录。

## 业务规则

1. 草稿或已退回用例可以发起评审，提交时必须指定 1–20 名可用评审人。
2. 评审人范围为项目内测试经理，以及具有全局权限的管理员、超级管理员。
3. 任务采用全员通过规则：所有指定评审人通过后，用例变为“已批准”；任一评审人退回后，本轮立即结束，其余待办取消，用例变为“需修改”。
4. 任务绑定提交时的 `TestCaseAssetVersion`，任务详情始终展示该版本快照，不受后续内容变化影响。
5. 评审期间修改内容、脚本、归类或标签，会取消旧任务并使用例回到草稿；修改后生成新用例版本，再发起下一轮评审。
6. 已产生评审记录的用例不允许物理删除，应通过废弃保留审计链路。

## 数据结构

### `case_review_tasks`

- `project_id`、`case_asset_id`：项目和用例关联。
- `case_version_id`、`case_version`：绑定不可变版本及可读版本号。
- `round`：同一用例的评审轮次。
- `status`：`pending`、`approved`、`changes_requested`、`cancelled`。
- `approval_rule`：当前固定为 `all`。
- `submitted_by`、`submission_comment`、`submitted_at`、`due_at`、`completed_at`：提交和时限信息。
- 数据库部分唯一索引保证同一用例最多只有一个进行中的任务。

### `case_review_assignments`

- 一条记录对应一名评审人。
- `status`：`pending`、`approved`、`changes_requested`、`cancelled`。
- `comment`、`decided_at`：个人评审意见和提交时间。
- `(task_id, reviewer_id)` 唯一，避免重复指派。

### `case_review_events`

新增 `task_id`、`case_version_id`、`case_version`，使提交、通过、退回和取消事件可以追溯到具体任务及版本。

数据库升级脚本为 `backend/alembic/versions/023_case_review_tasks.py`。升级时会把历史待评审用例迁移为单人评审任务；没有可用评审人的历史数据会安全退回草稿。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/cases/reviewers?project_id=` | 查询项目可选评审人 |
| `POST` | `/api/cases/{case_id}/review-tasks` | 指定评审人并创建任务 |
| `GET` | `/api/cases/review-tasks` | 查询个人待办、本人发起或项目全部任务 |
| `GET` | `/api/cases/review-tasks/{task_id}` | 获取任务、评审进度及冻结版本 |
| `POST` | `/api/cases/review-tasks/{task_id}/decision` | 指定评审人提交通过或退回结论 |
| `GET` | `/api/cases/{case_id}/review-tasks` | 获取用例的全部评审轮次 |

原有 `submit-review`、`review`、`adopt` 和 `adopt-batch` 接口继续保留，并映射到正式评审任务，供旧客户端平滑过渡。

## 前端入口和交互

- 用例列表“提交评审”打开评审任务表单，可选择多人、截止时间和提交说明。
- “待我评审”只显示当前用户被指派且尚待处理的任务，不再展示项目全部待评审用例。
- 评审抽屉展示轮次、绑定版本、提交信息、多人进度、冻结请求/步骤与断言；只有指定且未提交结论的评审人可操作。
- 用例详情新增“评审任务”页签，可查看所有历史轮次。
- 指派、完成和取消会生成站内通知，通知链接可直接打开对应评审任务。

## 验证范围

- 多人任务创建、版本冻结和指派通知。
- 非指定人员禁止提交结论。
- 全员通过后批准用例。
- 任一退回后终止本轮并取消其余待办。
- 修改后以新版本发起下一轮。
- 项目评审人范围隔离。
- 前端 TypeScript 检查与生产构建。
