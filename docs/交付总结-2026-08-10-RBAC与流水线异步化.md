## 二、需求 1：企业级 RBAC

### 2.1 角色体系（7 种）

| 枚举值 | 中文名 | 定位 |
|--------|--------|------|
| `super_admin` | 超级管理员 | 最高权限，管理操作**立即生效**，同时具备审核权 |
| `admin` | 系统管理员 | 可发起用户管理操作，但**需审核员审批后生效** |
| `test_manager` | 测试经理 | 测试业务管理 |
| `tester` | 测试工程师 | 执行测试、查看报告 |
| `developer` | 开发工程师 | 查看缺陷、代码分析 |
| `auditor` | 审核员 | 审批管理类变更请求 |
| `viewer` | 只读用户 | 仅查看 |

> 枚举值全部小写。旧库升级时 `init_db()` 会用 AUTOCOMMIT 连接执行
> `ALTER TYPE userrole ADD VALUE IF NOT EXISTS ...` 补齐 3 个新值（失败仅告警不中断）。

### 2.2 审批流设计（按用户确认的方案：仅管理类操作需审批）

```
需审批（admin 发起 → pending → auditor/super_admin 审批 → 落地）
  ├─ 新建用户   create_user
  ├─ 删除用户   delete_user
  └─ 修改角色   change_role

无需审批（立即生效）
  ├─ 用户改自己的个人资料   PUT /api/auth/me
  ├─ 用户改自己的密码       PUT /api/auth/me/password
  ├─ 启用/禁用用户          PUT /api/auth/users/{id}/status
  └─ super_admin 的所有管理操作
```

审批结果会通过站内通知（Notification）推送给发起人。

### 2.3 API 清单

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/auth/users` | manager | 用户列表 |
| POST | `/api/auth/users`（= `/register`） | manager | 新建用户（admin 走审批） |
| DELETE | `/api/auth/users/{id}` | manager | 删除用户（admin 走审批；禁删自己/超管） |
| PUT | `/api/auth/users/{id}/role` | manager | 改角色（admin 走审批） |
| PUT | `/api/auth/users/{id}/status` | manager | 启用/禁用，立即生效 |
| PUT | `/api/auth/me` | 任意登录用户 | 改自己资料 |
| PUT | `/api/auth/me/password` | 任意登录用户 | 改自己密码 |
| GET | `/api/change-requests` | auditor/super_admin | 变更请求列表（可按 status 过滤） |
| POST | `/api/change-requests/{id}/approve` | auditor/super_admin | 通过并落地 |
| POST | `/api/change-requests/{id}/reject` | auditor/super_admin | 驳回（带理由） |

> ⚠️ 路由约定：`change_request.py` 的 `APIRouter()` **不带 prefix**，prefix 由 `main.py` 统一提供，否则路径会重复。

## 三、需求 2：启动测试卡死修复

### 3.1 根因

`backend/app/api/test_run.py` 原先用 `asyncio.create_task(_execute_full_pipeline(...))` 启动流水线，
而流水线内部的 `fetch_code()` 是**同步阻塞**调用（Git/SVN 拉代码），直接占死 FastAPI 的事件循环。
后果是**整个后端 API 无响应**，前端表格的 `v-loading` 遮罩永远不消失，页面看起来"卡死"。

### 3.2 修复

新建 `backend/app/modules/pipeline.py`：

```python
@app.task(bind=True, max_retries=2)
def run_test_pipeline(self, test_run_id: str, req_dict: dict):
    # 10%  fetch_code   （同步，在 worker 进程里跑，不影响 API）
    # 25%  analyze_project  （asyncio.run 包裹）
    # 40%  generate_all     （asyncio.run 包裹）
    # 50%  execute_all      （原有 Celery chain）
    # 异常兜底：Redis 写 failed + TestRun 置 FAILED
```

配套改动：
- `celery_app.py` 的 `include` 列表加入 `"app.modules.pipeline"`（**新任务模块不加进来 worker 收不到**）
- `test_run.py` 改为 `run_test_pipeline.delay(test_run_id, req.model_dump())`，删除原 `_execute_full_pipeline`
- 前端 `TestRun.vue` 提示改为"测试已在后台启动，可在列表中查看实时进度"，无全屏 loading 锁

API 现在**毫秒级返回**，流水线在 celery-worker 独立进程执行，进度通过 Redis + `/progress` 端点轮询展示。

## 七、部署步骤（Ubuntu 22.04）

```bash
cd /opt/ai-test-platform

# 1. 拉取最新代码
git pull    # 或重新上传项目目录

# 2. 清库重建（推荐，避免 PG userrole 枚举扩值的边缘问题）

# 3. 构建并启动
docker compose up -d --build

# 4. 查看状态
docker compose ps
docker compose logs -f backend celery-worker
```
