# AI 自动化测试平台 · 企业级成熟度评估与改进建议

> 评估日期：2026-09-16
> 评估对象：`D:\code\ai-test-platform`（仓库 Guo-junjie/ai-test-platform）
> 运行实例：http://192.168.125.128:3000（前端 Nginx） / :8000（FastAPI）
> 评估方式：源码只读审查（backend 158 个 .py / frontend 35 个 view / 46 条路由）+ 线上实例探测

## 0. 实测结论（线上实例）

| 探测项 | 结果 | 含义 |
|---|---|---|
| `GET /api/health` | `{"status":"healthy","env":"development"}` | 平台跑在 **development 环境档**，非生产档 |
| `GET /docs`（未鉴权） | HTTP 200 | **API 文档全网可读**，159 个端点全部暴露 |
| `GET /openapi.json` | 159 条路径 / 30 个资源组 | API 面很大，但无版本化前缀 |
| `GET /api/projects`（无 Token） | HTTP 401 | 业务接口鉴权有效 ✅ |
| 前端 `:3000` | HTTP 200，`/api/` 经 Nginx 反代 | 部署链路可用 ✅ |
| `POST /api/auth/login`（gjj/123456） | `{"detail":"用户名或密码错误"}` | 该账号在线上实例 **未通过认证**，需确认账号是否已创建或密码已变更 |

能力实现是**真实的、不是玩具**：执行引擎（Celery chain+group + Locust 压测 + 断言引擎）、覆盖率（手写 JaCoCo TCP 协议 + varint 解码，支持 JaCoCo/Cobertura/Go coverprofile）、质量门禁（6 条规则）、缺陷 AI 根因分析、8 种框架代码适配器、RAG 知识库 —— 均已落地。

**结论：这是一个"功能做得比"工程底座"跑得快的项目"。核心差距不在能力数量，而在 ①执行隔离与安全 ②端到端可用性 ③部署运维成熟度。**

## 1. 评估基准：企业级测试平台六维标准

| 维度 | 企业级要求 |
|---|---|
| 功能完整性 | 测试资产（用例/数据/脚本）管理、编排与调度、环境管理、执行与隔离、结果分析、缺陷闭环、质量门禁、CI/CD 集成 |

## 2. P0 · 阻断级问题（建议 2 周内处理）

### P0-1　凭据与密钥治理失效（**最高优先级**）

| 项 | 内容 |
|---|---|
| **问题** | ① `.local-tools/vmssh.py` 写死 SSH 主机/账号/口令，且 `.gitignore` **未忽略 `.local-tools/`**（仅忽略了 `.env` 与 `.ssh_*.py`），存在入库泄露风险；② `config.py` 中 `AES_ENCRYPTION_KEY` 默认值为 32 个 `"0"` —— 数据库凭据"加密"形同虚设；③ `docker-compose.yml:22/54/72` 三处弱口令兜底；④ Redis 未设密码（`.env` 中 `REDIS_PASSWORD` 为空）；⑤ 根目录存在 `.env`（明文库口令）、`.ssh_helper.py`（明文口令 + sudo 回显）、`.local-tools/cleanup.py`（全表 DELETE 清库脚本）。 |
| **影响** | 一次性泄露即导致数据库/对象存储/被测环境全线失守；弱口令使"企业级"定位不成立。 |
| **改进方向** | ① 立即把 `.local-tools/`、`.env*`、`*.log` 补进 `.gitignore`，并**轮换所有已出现过的口令**；② 密钥改为启动时从 Secret Store 注入（Docker secrets / Vault / K8s Secret），删除代码内默认值；③ 启动时**强校验**：`AES_ENCRYPTION_KEY` 为默认值 / 口令长度 <12 → 直接 `fail-fast` 拒绝启动；④ 给 Redis 设密码，管理台端口不对公网绑定。 |

### P0-2　生产环境实际跑在开发档

| 项 | 内容 |
|---|---|
| **问题** | 线上实测 `env=development`。`docker-compose.yml`（自称"生产基线"）中 backend 仍以 `--reload` 启动并 bind mount 源码（`:106,110`、`:129,148,163`）；CORS 为 `allow_origins=["*"]` + `allow_credentials=True` 的**非法组合**（`main.py:104-105`）；`/docs`、`/redoc`、`/openapi.json` 未关闭（实测 200 未鉴权）。 |
| **影响** | 无版本化、无回滚；任意站点可携带凭据调用 API；159 个端点结构对攻击者完全透明；`--reload` 在生产会带来文件监听开销与热重载不可控。 |
| **改进方向** | 拆 `docker-compose.prod.yml` 覆盖层：去掉 `--reload` 与源码挂载，改为镜像内固定产物 + 镜像 tag 版本化；`APP_ENV=production` 时关闭 docs/redoc/openapi（或加管理员鉴权），CORS 改白名单；启动日志打印当前环境档，避免"以为在生产、实际在开发"。 |

### P0-3　执行隔离不足：被测代码可反控平台

| 项 | 内容 |
|---|---|
| **问题** | `docker-compose.dev.yml:20` 把 `/var/run/docker.sock` 挂进 `celery-worker`（等价宿主 root）；即便生产基线，worker 仍与平台**同网络、同数据卷、同容器镜像**运行（`:128-134`）。`env_adapters.py:63` 用 `docker.from_env()` 起被测服务。 |
| **影响** | 被测产品代码（尤其来自 SVN/GitHub 的第三方代码）在测试过程中可读取平台数据库凭据、访问内网、反控宿主。这是企业级测试平台的红线。 |
| **改进方向** | 引入**独立 Runner**：执行侧以独立节点/容器运行，仅暴露任务协议（拉任务 → 回传结果）；容器加固（`cap_drop: ALL`、`read_only: true`、`no-new-privileges`、独立 network namespace、临时工作卷）；生产禁止挂 docker.sock，改用受限 remote API 代理或 Kaniko/gVisor；被测服务与平台数据面网络分段。 |

### P0-4　"假绿"风险：失败被吞，空结果记为通过

| 项 | 内容 |
|---|---|
| **问题** | `engine.py:567-569/626-628/684-688` 把异常吞成 `results=[]`，`aggregate` 汇总 `total=0` 后仍在 `engine.py:795` 标记 `completed`；`max_retries` 在 `engine.py:363/532/585/645` 声明但**全仓无 `self.retry()` 调用** —— 重试是死配置。 |
| **影响** | 测试失败或环境异常会呈现为"执行完成"，质量门禁与趋势数据被污染。对测试平台而言，这是**信任崩塌级**问题。 |
| **改进方向** | ① 异常必须向上传播并落地为 `failed` + 失败原因；② 增加断言：`total == 0` 或存在未执行用例时**禁止**标记 completed；③ 接通 `self.retry()`（配合 `acks_late=True` + 幂等键）；④ 质量门禁增加"结果完整性"输入项。 |

### P0-5　数据库 Schema 双轨制

| 项 | 内容 |
|---|---|
| **问题** | `models/database.py:1306-1612` 的 `init_db()` 在运行时执行 `ALTER TABLE` / `ALTER TYPE ... ADD VALUE`，与 `alembic/versions/001~006` 并存。 |
| **影响** | 同一套库有两条演进路径，迁移不可复现、无法回滚，环境间漂移不可避免。 |
| **改进方向** | Alembic 作为**唯一**演进来源；`init_db()` 只保留幂等的种子数据与只读校验；把现有运行时 ALTER 补成正式迁移脚本。 |

### P0-6　授权只到 project_id，无租户与所有权校验

| 项 | 内容 |
|---|---|
| **问题** | 隔离维度仅 `project_id`（`models/database.py:186/305/648`），无 `tenant_id`、无统一"资源所有权"依赖函数；列表查询靠路由自己记得加过滤条件。 |
| **影响** | 159 个端点中只要有 1 处漏加过滤，就是水平越权。RBAC 有 7 种角色，但**行级权限**未成体系。 |
| **改进方向** | 抽象 `require_project_access(project_id, user)` 依赖并强制所有项目域端点使用；引入 `tenant_id`（或至少 owner/team）字段与统一查询基类；补充越权测试用例。 |

## 3. P1 · 严重影响可用性与完整性（建议 1~2 个月内）

### P1-1　主流程割裂、无"下一步"引导 —— **这是"难用"的第一根因**

| 项 | 内容 |
|---|---|
| **问题** | 完成一次测试需跨 **8+ 页面**：登录 → 建项目 → 传代码 → 建环境 → 解析文档 → 生成用例 → 手写断言 → 加计划 → 发布 → 执行 → 轮询 → 看报告。全站**只有 `DocReview.vue:13` 一个"下一步"按钮**；`ProjectContext.vue:7-29` 四张卡片跳转**不带 project_id**，用户每次都要重新选项目；`TestRun.vue:13-18` 用整段文字教程教用户"去项目管理点执行"；`ProjectQuality.vue:29-34` 是纯 4 个跳转卡、零数据。 |
| **影响** | 用户必须脑中记住流程并在页面间手工搬运上下文 —— 这正是"较难用"的体感来源。 |
| **改进方向** | 在项目工作区内做**状态机驱动的流水线向导（Stepper）**：接入 → 解析 → 用例 → 计划 → 执行 → 报告，每步显示完成度与阻塞原因，并提供"下一步"直达按钮（带 `project_id`）；未完成前置步骤时按钮禁用并说明原因；提供"一键跑通"（默认参数直接跑完全链路）入口给演示与冒烟场景。 |

### P1-2　要求用户手写 JSON / 技术参数

| 项 | 内容 |
|---|---|
| **问题** | `CaseLibrary.vue:148,151` 断言要手写 JSON；`Scenario.vue:130` 场景步骤手写 JSON；`ScheduledTasks.vue:78` 手填 cron 表达式、`:116` 必填服务地址；`Coverage.vue:419` 要填探针令牌环境变量名；`ProjectPlans.vue:74` 要填 commit SHA；`DatabaseManage.vue` 要填 host/port/库名。 |
| **影响** | 业务测试人员无法独立完成，平台实际只能由开发人员操作，企业级"测试人员自助"目标落空。 |
| **改进方向** | 断言构造器（字段选择 + 操作符 + 期望值，可切"高级 JSON 模式"）；场景步骤可视化编排（拖拽/表单，JSON 作为只读产物）；cron 可视化选择器（同时展示未来 5 次执行时间）；SHA 改为"分支/标签下拉 + 最近提交列表"；数据库连接改为"连接串粘贴自动解析 + 一键连通性测试"。 |

### P1-3　列表普遍缺分页、搜索、批量与导出

| 项 | 内容 |
|---|---|
| **问题** | `TestRun.vue`、`Projects.vue`、`SourceManage.vue`、`ScheduledTasks.vue`、`DatabaseManage.vue`、`Approvals.vue`、`ProjectRuns.vue`、`ProjectPlans.vue` **均无 `el-pagination`**（对比 `CaseLibrary.vue:119` 有）；`Projects.vue:14` 无关键词搜索；`CaseLibrary.vue:103-117` 单行 8 个按钮、宽 480px，语义相近（批准/退回/废弃/删除）易误点。 |
| **影响** | 数据量上来后翻不动、找不到、易误操作；演示阶段看不出来，上线即痛。 |
| **改进方向** | 抽一个统一 `ProTable` 组件（分页 + 关键词搜索 + 列筛选 + 排序 + 批量选择 + 导出 CSV），全站列表替换；行操作收敛为「主操作（1~2 个）+ 更多下拉」，删除类操作加二次确认与影响说明。 |

### P1-4　错误静默，故障伪装成"0"

| 项 | 内容 |
|---|---|
| **问题** | `Dashboard.vue:166-187` 空 `catch {}`；`ProjectOverview.vue:191-201` 五处 `catch(() => {})`。 |
| **影响** | 后端异常时看板显示 0，用户误判"没数据"而非"接口挂了"，排障方向被误导。 |
| **改进方向** | 统一 `useRequest` 封装：错误态组件 + 局部重试按钮 + 全局错误提示；禁止空 catch（加 lint 规则）；关键看板加"数据刷新时间 + 数据来源状态"。 |

### P1-5　无新手引导、无术语解释、无面包屑与全局搜索

| 项 | 内容 |
|---|---|
| **问题** | 全站无 Onboarding Tour；`Layout.vue:118` 注释明示"面包屑已移除"；46 条路由只能靠侧栏逐层找；SUT / 探针 / 质量门禁 / JaCoCo 等术语无 tooltip 词条；空状态基本只有 `el-empty` 默认文案，不给行动入口。 |
| **影响** | 新用户第一次进入不知道该干什么；老用户找不到页面。 |
| **改进方向** | 首次登录 3 步引导（建项目 → 连模型 → 跑第一条测试）；面包屑 + 命令面板（`Ctrl/Cmd+K` 全局跳转与搜索）；术语词条统一词典 + 帮助中心侧滑；每个列表空态改为"引导卡 + 主操作按钮"。 |

## 4. P2 · 架构规范与工程质量（持续治理）

### P2-1　单体巨文件、无分层

| 项 | 内容 |
|---|---|
| **问题** | 后端：`models/database.py` 单文件 1600+ 行承载 40+ 模型，路由直接操作 ORM，无 Service/Repository 层；`engine.py:704-924` 的 `aggregate_results` 是 220 行 god-function，串行做覆盖率/报告/事件/计划快照/CI 回调。前端：`TestRun.vue` 1400 行、`Coverage.vue` 1293 行、`KnowledgeBase.vue` 1273 行、`Projects.vue` 930 行。 |
| **改进方向** | 后端按领域拆包（`domain/` 模型 + `repository/` 数据访问 + `service/` 业务 + `api/` 薄路由）；`aggregate_results` 拆成 Celery 任务链（覆盖率 → 报告 → 通知 → CI 回调各自独立、可重试）。前端按子组件 + `composables` 拆分，单文件控制在 400 行内。 |

### P2-2　API 契约不统一

| 项 | 内容 |
|---|---|
| **问题** | 无版本化（全 `/api/*`，无 `/v1`）；prefix 冲突（`environments.py` 与 `report_analysis.py` 共用 `/api`，`main.py:176/256`）；`/api/docs` 与 FastAPI 内置 `/docs` 语义撞名；`change_request` 注册漏 `tags`；索引路由 `@router.get("")` 与 `@router.get("/configs")` 风格混用，靠 `redirect_slashes=True` 兜 307；响应体不统一（`test_run.py:151/347`、`audit.py:23` 返回裸 dict）；无业务错误码枚举；`schemas/` 仅 4 个文件，无分页/响应公共模型；分页参数不一致（14 处有 `page/page_size`，`test_run.py:78`、`project.py:69`、`notification.py:134` 只有 `limit` 无 `page`）。 |
| **改进方向** | 统一 `/api/v1` 前缀；定义 `ApiResponse[T]` 与 `Page[T]` 泛型 + `ErrorCode` 枚举；所有列表统一 `page/page_size`（`ge/le` 校验）；OpenAPI 分组 tag 补齐；废弃 `redirect_slashes` 依赖，前端 URL 规范化。 |

### P2-3　前端类型安全与状态管理

| 项 | 内容 |
|---|---|
| **问题** | `: any` / `as any` 共 **451 处**；`api/index.ts` 全量 `data: any`，无请求/响应 DTO；响应包 `{code,data,message}` 处理不一致 —— 拦截器直返 `response.data`（`:24`），调用方有的判 `res.code===0`（`stores:157`）有的直取 `res.data`（`Dashboard.vue:160`）；8 个 view 用 `defineComponent` 与 27 个 `<script setup>` 混用；`stores/index.ts` 的 `sidebarCollapsed` 未被 `Layout.vue` 使用（`Layout.vue:169` 自己 `ref`）。 |
| **改进方向** | 拦截器统一解包并抛业务异常，调用方只消费强类型 DTO；用 OpenAPI 生成 TS 类型；全量迁到 `<script setup>`；状态收归 Pinia，组件不重复持有全局状态；`eslint` 开 `no-explicit-any` 为 warn 并逐步清零。 |

### P2-4　重复代码与死代码
